## Q6 Where tokens go in coding agents
- Q6 8 LLMs (Claude Sonnet 3.7/4/4.5, GPT-5/5.2, Qwen3-Coder, Kimi-K2, Gemini-3-Pro) on 500 SWE-bench Verified tasks: agentic coding uses "3500x more tokens than a typical single-round reasoning task" and "1200x more than a multi-round chatting task"; input tokens dominate cost "even with caching enabled"; cache-read tokens are the dominant cost category in all phases; "the most expensive run is ~2x the cheapest" on identical tasks (up to 30x token variance per snippet/summary); "accuracy increases modestly from MinCost to LowerCost, but then saturates in higher-cost settings"; self-prediction correlation up to 0.39 and "all the models systematically underestimate"; Claude Sonnet 4.5 and Kimi-K2 use "over 1.5 million more tokens" than GPT-5 on shared tasks -- https://arxiv.org/html/2604.22750v2 -- tier A
- Q6 Search snippet of same paper family: input:output ratio "exceeding 150:1"; "read operations dominating token consumption at 76.1%" (snippet, unfetched; only the 76.1% figure is unverified) -- https://longjubai.github.io/agent_token_consumption/ -- tier B
- Q6/Q5 Three cost-inefficient behaviors: Subsumed Retrieval ("retrieving code fully covered by previous retrievals", 5.01-11.41% of task cost), Similar Script Generation (up to 9.57%), Test Re-Execution (up to 5.39%); together "affect 79.00%-98.00% of coding tasks and account for up to 22.75% of task monetary cost". Mitigation: developer-designed Skills gave "cost savings of 7.88%-41.73%" with only one small Pass@1 drop (-1.50 pp); agent-synthesized skills "at most 22.32%"; structure-aware retrieval (CodeGraph) INCREASED cost "up to 28.14%" in several cases -- https://arxiv.org/html/2609.30725v1 -- tier A

## Q3/Q5 history processors and context pruning
- Q5/Q3 SWE-Pruner: lightweight 0.6B-parameter neural "skimmer" selects relevant code lines per task goal; abstract claims "23-54% token reduction on agent tasks like SWE-Bench Verified while even improving success rates, and up to 14.84x compression on single-turn tasks like LongCodeQA with minimal performance impact" (needs a trained model + hook point; not usable as a stock Claude Code setting) -- https://arxiv.org/abs/2601.16746 (accessed 2026-10-02) -- tier A (abstract only)

## Q4 prompt compression
- Q4 LongLLMLingua: "boosts performance by up to 21.4% with around 4x fewer tokens in GPT-3.5-Turbo"; "94.0% cost reduction in the LooGLE benchmark"; on ~10k-token prompts at 2x-6x compression, end-to-end latency 1.4x-2.6x faster (snippet, unfetched) -- https://arxiv.org/pdf/2310.06839v2 ; https://aclanthology.org/2024.acl-long.91.pdf -- tier A via snippet. Domain is QA/RAG over prose, not agent tool output or code.
- Q4 LLMLingua-2: task-agnostic token-classification compressor distilled from GPT-4, 2x-5x compression "while maintaining accuracy" on QA/summarisation/math; 3x-6x faster than LLMLingua (snippet, unfetched) -- https://arxiv.org/pdf/2403.12968 -- tier A via snippet. README claims "up to 20x compression with minimal performance loss" (snippet) -- https://github.com/microsoft/LLMLingua -- tier B
- Q4 Compression vs caching: query-aware compression "produce[s] a different compressed prefix for every query ... mechanically invalidates the prefix-strict cache on every call"; cost model predicts query-aware compression beats naive caching only at high ratios (r>=6); Cache-Aware Prompt Compression (query-agnostic compression + explicit cache_control) reports 51.7% cost reduction at r=3 on an enterprise tool-using assistant with a 94k-token tools-schema prefix (snippet, unfetched) -- https://arxiv.org/html/2607.15516v1 -- tier A via snippet
- Q4 Implication (Interpretation): in Claude Code, compressing the stable prefix (CLAUDE.md, tool schemas) once and keeping it byte-stable is compatible with caching; per-turn rewriting of history is not.

## Q7 plan-then-execute, harness design
- Q7/Q3 Harness study: 176 matched settings, four models, SWE-Bench Verified + Terminal-Bench 2.1. "Context management becomes increasingly valuable as the context-window budget tightens, with most of its benefit coming from preventing context-overflow failures"; rule-based elision followed by LLM summarisation gave the strongest efficiency gains. Planning "shifts from an accuracy scaffold for weaker models to a cost saver for stronger models, with little change in accuracy". Bash-capable models do fine with a bash-only interface at "substantially lower costs" -- https://arxiv.org/abs/2609.20804 (accessed 2026-10-02) -- tier A (abstract)
- Q7 Planning on SWE-bench (snippet, unfetched): Nemotron-3 30B +11.6 pp success from planning; for Nemotron-3 550B and Mistral-Medium-3.5-128B planning cuts cost ~30% and ~32% with success down only 2.0 and 0.4 pp. Planner quality dominates executor quality ("A weak planner constrains the entire system") -- https://arxiv.org/pdf/2609.20804 and related snippet -- tier A via snippet
- Q7 Practitioner claims (snippet, unfetched, no method): planner-executor "approximately 4.4x cost reduction on execution-side spend"; "30-60 percent in tokens on multi-tool tasks"; "~30% of tokens go to planning turns while 70% go to execution" in 40 app builds -- https://www.morphllm.com/multi-agent-model-routing -- tier C

## Q5 retrieval: LSP / symbol-level / maps
- Q5 CONTRADICTS the Claude Code costs doc's qualitative claim: "Does a Language Server Save Tokens for Coding Agents?" (Claude Opus 4.8, Sonnet 4.6, Haiku 4.5; Python + TypeScript repos): LSP increases tokens "+6% to +118%" vs grep-based lexical retrieval on symbol localization; on reference completeness LSP "buys precision but not token savings" and reduces tokens only "for the weakest model"; on multi-file renames grep is perfect while "a location-only LSP fails three-quarters of them by missing a call site"; models used grep on localization ("0-6% semantic use") and reached for LSP about half the time on reference tasks unprompted. Recommends "an adaptive router keyed on task class, model capability, and lexical noise" -- https://arxiv.org/abs/2608.13568 (accessed 2026-10-02) -- tier A
- Q5 Codebase-Memory (tree-sitter knowledge graph via MCP): "reduced agent token use by roughly 10x and tool calls by 2.1x across 31 repositories"; a repo map used 87 tokens instead of ~12,000 for all source (snippet, unfetched; own benchmark, answer-quality metric not seen) -- https://arxiv.org/pdf/2603.27277 -- tier B via snippet
- Q5 Serena (LSP-to-MCP bridge, 40+ languages) claims symbolic editing is "much more token-efficient" -- no measurement found -- https://github.com/oraios/serena (snippet, unfetched) -- tier C
- Q5/Q6 Structure-aware retrieval (CodeGraph) raised cost up to 28.14% in the 2609.30725 study (see Q6) -- consistent with the LSP paper: graph/LSP tooling is not a free token saver.
