## 1. TEMPORAL

### T1. History limits and Continue-As-New triggers (DATA MODEL / INVARIANT)
Source: temporal v1.32.0 `common/dynamicconfig/constants.go`.
| key | default |
|---|---|
| `limit.historySize.error` | 50 MiB (terminates execution) |
| `limit.historySize.warn` | 10 MiB |
| `limit.historyCount.error` | 50*1024 = 51,200 events |
| `limit.historyCount.warn` | 10*1024 = 10,240 events |
| `limit.historySize.suggestContinueAsNew` | 4 MiB ("in workflow task started event") |
| `limit.historyCount.suggestContinueAsNew` | 4*1024 = 4,096 events |
| `limit.mutableStateSize.error` / `.warn` | 8 MiB / 1 MiB |
| `limit.blobSize.error` / `.warn` | 2 MiB / 512 KiB per event payload |
| `limit.numPendingActivities.error` | 2000 |
| `limit.numPendingSignals.error` | 2000 |
| `limit.maxIDLength` | 1000 (WorkflowID, RequestID, Identity, ...) |
Pattern: THREE graded thresholds — *suggest* (server sets `suggest_continue_as_new` on WorkflowTaskStarted so the workflow code rolls over voluntarily), *warn* (logs/metrics), *error* (server terminates). The suggestion arrives well below the hard cap (4 MiB vs 50 MiB) so the rollover happens by the workflow's own choice at a safe point.
Continue-As-New semantics (well-established, see §T5 for proto): same WorkflowID, NEW RunID, fresh history; carries only explicit input (+memo/search attributes/headers); pending activities, timers, signals-not-yet-read are NOT carried.
- Class: INVARIANT (bounded history per run) + ALGORITHM (graded suggest/warn/error).
- UWCP mapping: **PARTIAL.** UWCP already has "epoch = bounded run" (job budget 45 min + context wall) and a brief/capsule as the explicit carried state (≈ CAN input). MISSING: (a) a bound on the *goal log itself* per workstream — the log is append-only forever, and a long workstream's `project_epochs(state)` replays all of it; no suggest/warn/error thresholds on log bytes/event count; (b) byte+token bound exists on the brief ("refuse, never truncate") = the *error* rung, but there is no *suggest* rung that tells the epoch to hand off early. Gap name: **G-T1 unbounded goal log + no pre-wall suggestion signal.** Falsification test: synthesise a goal log with 50k epoch events and assert `project_epochs` time/memory under a stated bound, or that a compaction/snapshot event exists; and assert the runner receives a `suggest_handoff` flag when capsule bytes cross e.g. 50% of the refuse bound.

### T2. Shard ownership fencing by range_id (PROTOCOL PATTERN / INVARIANT) — the direct analogue of UWCP fence generation
Sources: temporal v1.32.0 `common/persistence/sql/shard.go` (`lockShard`, `readLockShard`), `common/persistence/sql/execution.go` (`txExecuteShardLocked`), `service/history/shard/context_impl.go` (`renewRangeLocked`, `handleWriteErrorLocked`, `acquireShard`).
- Acquisition: `renewRangeLocked` does `updatedShardInfo.RangeId++` and persists via `UpdateShard(... PreviousRangeID: previousRangeID)` — a CAS on the previous range id. Before renewing it calls `s.taskKeyManager.drainTaskRequests()` (in-flight writes under the old range are drained first).
- Every execution write runs inside `txExecuteShardLocked(ctx, op, shardID, rangeID, fn)` which first calls `readLockShard(ctx, tx, shardID, rangeID)`; that function does `if rangeID != oldRangeID { return &persistence.ShardOwnershipLostError{... "Failed to lock shard. Previous range ID: %v; new range ID: %v"} }`. i.e. **the fence is checked inside the same DB transaction as the write**, with a row lock on the shard row — not before it.
- Row-level: execution rows also carry `DBRecordVersion`; `lockAndCheckExecution` (execution_util.go) returns `WorkflowConditionFailedError` on mismatch; `assertRunIDAndUpdateCurrentExecution` returns `CurrentWorkflowConditionFailedError` if the current-run pointer moved. Two fences: coarse (owner generation) + fine (record version).
- Task IDs are allocated from the owned range (taskKeyManager, conditioned on `getRangeIDLocked()`), so IDs issued by a deposed owner can never collide with the new owner's.
- On `ShardOwnershipLostError` (read or write) the shard context transitions to stop (`stopReasonOwnershipLost`) — **the deposed owner stops itself; it does not retry**. `acquireShard` retries with exponential backoff (1 s, expiry 5 min) but `ShardOwnershipLostError` is non-retryable (`return false`).
- Class: PROTOCOL PATTERN (fencing token = monotonic generation, checked atomically with the effect) + INVARIANT (a write by generation g succeeds only if stored generation == g).
- UWCP mapping: **PARTIAL.** UWCP plans "monotonic fence generation per epoch, receipts refused if fence stale" and "runner verifies it before each side effect". Two gaps: (1) **G-T2a check-then-act**: the runner checks the fence *before* the side effect, on GEX44, against a VPS store — the effect (git commit/push, capsule upload) is not in the same atomic unit as the check, so a fence bump between check and effect is not refused. Temporal puts the check *inside* the write transaction. UWCP's only truly atomic point is ingest at the home (harvest refuses stale fence) — so the design must state that **effects on the node are provisional, and only the home's ingest under the log's lock is the commit point**; anything the node pushes externally (git remote, artifacts) needs its own fence (e.g. push to a ref named by fence generation, promoted only by the home). (2) **G-T2b deposed-owner self-stop**: nothing in §14 says a runner that sees a stale fence stops *all* further effects and exits (Temporal's stopReasonOwnershipLost); it only says receipts are refused. Falsification tests: (a) bump the fence between the runner's pre-check and its commit, assert the home refuses the receipt AND no ref outside `refs/uwcp/<goal>/<fence>` was moved; (b) runner observing stale fence mid-epoch exits non-zero within one progress interval and emits no further receipts.

### T3. Stale activity completion rejection — task token (PROTOCOL PATTERN / INVARIANT)
Sources: temporal v1.32.0 `proto/internal/temporal/server/api/token/v1/message.proto` (message `Task`), `service/history/api/respondactivitytaskcompleted/api.go`, `service/history/api/activity_util.go` (`IsActivityTaskNotFoundForToken`).
- Token fields: `namespace_id=1, workflow_id=2, run_id=3, scheduled_event_id=4, attempt=5, activity_id=6, workflow_type=7, activity_type=8, clock=9 (VectorClock), started_event_id=10, version=11, started_time=12, start_version=13, component_ref=14, activity_attempt_stamp=15`. Opaque blob given to the worker; completion must echo it. It names the **run** (not only the workflow), **which scheduled activity**, **which attempt**, and the **failover version**.
- Rejection ladder in respondactivitytaskcompleted:
  1. `if !mutableState.IsWorkflowExecutionRunning()` -> `ErrWorkflowCompleted` (run closed ⇒ no completion accepted ≈ UWCP "epoch ended").
  2. `if !isRunning && scheduledEventID >= mutableState.GetNextEventID()` -> `consts.ErrStaleState`: the *server's cached* state is behind the token; reload and retry. NOT a rejection of the worker.
  3. `if !isRunning || api.IsActivityTaskNotFoundForToken(token, ai, &isCompletedByID)` -> `ErrActivityTaskNotFound`. Helper returns true when `ai.StartedEventId == common.EmptyEventID` (never started), `token.Attempt != ai.Attempt` (a newer attempt exists — late completion of attempt N after N+1 was scheduled is dropped), `token.GetStartVersion() != ai.GetStartVersion()`, or `token.GetVersion() != ai.GetVersion()`.
- Class: PROTOCOL PATTERN (the completion carries the full identity of the attempt it completes; the authority compares against its own record) + INVARIANT (at most one attempt's result is accepted per scheduled activity; a superseded attempt's result is refused, never merged) + FAILURE PATTERN (separate "your token is stale" = drop, from "my view is stale" = reload).
- UWCP mapping: **PARTIAL.** Fence generation + ended-epoch refusal ≈ Attempt + IsWorkflowExecutionRunning. MISSING: **G-T3a receipt identity completeness** — the receipt must echo (goal_id, epoch_id, fence generation, run_token, mission revision) and ingest must compare every field; a fence-only check passes a receipt for epoch E carrying a fence reused on E's retry. **G-T3b home-view staleness** — if harvest reads a cached projection, "receipt fence > projected fence" must reload-and-retry, not refuse and not accept. Tests: (1) receipt with correct fence and a previous epoch_id → refused `epoch_mismatch`; (2) receipt with fence greater than the projection → reload path observed (counter), then judged against the reloaded state.

### T4. Activity timeouts, heartbeat-as-checkpoint, worker death (ALGORITHM / DATA MODEL)
Source: temporalio/api `master` `temporal/api/command/v1/message.proto` (`ScheduleActivityTaskCommandAttributes`) — read 2026-09-25; revision not pinned by SHA (api repo master).
- `schedule_to_start_timeout`: "Limits the time an activity task can stay in a task queue before a worker picks it up." (queue wait, NOT retried by default — detects no worker.)
- `start_to_close_timeout`: "Maximum time an activity is allowed to execute after being picked up by a worker. This timeout is always retryable." (one attempt's budget.)
- `schedule_to_close_timeout`: "how long the caller is willing to wait ... Limits how long retries will be attempted." (whole-activity budget across attempts.)
- `heartbeat_timeout`: "Maximum permitted time between successful worker heartbeats." Worker death is detected by heartbeat timeout (fast) or StartToClose (slow); the attempt is failed with TIMEOUT and retried per `retry_policy`. The last recorded heartbeat *details* are delivered to the next attempt (SDK `activity.GetHeartbeatDetails` / `activity.info().heartbeat_details`), which is how a long activity resumes from a checkpoint instead of from zero.
- Class: ALGORITHM (four clocks: queue-wait, per-attempt, total, liveness) + DATA MODEL (heartbeat details = checkpoint owned by the server, not by the worker).
- UWCP mapping: **PARTIAL.** UWCP has: job budget 45 min (≈ StartToClose), "TTL counted from DISPATCH, queued jobs hold a reservation not a clock" (explicitly *rejects* a ScheduleToStart clock on the lease — good, matches Temporal's separation), start proof via ack + first progress record within a deadline (≈ first heartbeat), stall → LOST(stall) (≈ heartbeat timeout), `max_epochs/max_hours` (≈ ScheduleToClose). MISSING: **G-T4 queue-wait bound**: nothing bounds how long a uwcp-* job may sit queued (failover:never means it can queue forever behind a stuck job); Temporal's ScheduleToStart exists exactly for "no worker is polling". Also heartbeat details ≈ the progress file, but the progress file is on the node; after node death the next epoch starts from "last receipted capsule" — **checkpoint granularity = one epoch**; any in-epoch progress not in a receipt is lost (UWCP says so honestly in §14). Tests: queue a uwcp-* job behind a job that never finishes; assert status reaches `QUEUE_WAIT_EXCEEDED`/BLOCKED within the declared bound rather than staying DISPATCHING indefinitely.

### T5. Identity: WorkflowID vs RunID; start dedup; update dedup (DATA MODEL / INVARIANT)
Sources: temporalio/api `master` `temporal/api/enums/v1/workflow.proto`; `temporal/api/update/v1/message.proto`; temporal v1.32.0 `service/history/workflow/update/registry.go`.
- WorkflowID = business identity; RunID = one incarnation. Invariant in the proto comment: "it is *never* valid to have two actively running instances of the same workflow id." Two orthogonal policies: `WorkflowIdReusePolicy` (vs a *closed* run: ALLOW_DUPLICATE / ALLOW_DUPLICATE_FAILED_ONLY / REJECT_DUPLICATE; TERMINATE_IF_RUNNING deprecated) and `WorkflowIdConflictPolicy` (vs a *running* run: FAIL → `WorkflowExecutionAlreadyStartedFailure`, USE_EXISTING → return handle to the running one, TERMINATE_EXISTING). StartWorkflowExecution also carries a `request_id` so a retried identical start returns the same run instead of failing (conflict-policy USE_EXISTING generalizes this).
- Update: `Meta{update_id, identity}`; comment "An ID with workflow-scoped uniqueness for this Update." Registry `FindOrCreate` checks the in-flight map (`if upd := r.Find(ctx, id); upd != nil { return upd, true, nil }`) and completed outcomes (`r.store.GetUpdateOutcome(ctx, id)`) so a retry of an accepted/completed update returns the original outcome. Limits: `inFlightCount() >= maxInFlight` → "limit on number of concurrent in-flight updates has been reached"; `len(r.updates)+r.completedCount >= maxTotal` → "The limit on the total number of distinct updates in this workflow has been reached". **Dedup is per run: the registry is rebuilt per execution, so it does not survive Continue-As-New.**
- Class: DATA MODEL (two-level identity) + INVARIANT (≤1 running run per workflow id) + PROTOCOL PATTERN (idempotency key → return prior outcome, not error).
- UWCP mapping: goal_id ≈ WorkflowID, epoch_id ≈ RunID, run_token ≈ request_id. **COVERED** for "≤1 open epoch per goal" only if `begin()` refuses while `open_epochs(state)` is non-empty — verify; §14 "kill between intent and enqueue → probe by run_token → adopt | LOST, never duplicate" ≈ USE_EXISTING. **PARTIAL G-T5 operator-event dedup across epochs**: operator.* events (pause/cancel/re-pin) need an operator-supplied id deduped at the *goal* level, not per epoch — Temporal's per-run update dedup is a documented hole after CAN (a client retrying an update across the CAN boundary gets it applied twice). Test: submit the same `operator.pause` id twice with an epoch rollover between → exactly one pause event in the log.

### T6. Versioning / determinism (INVARIANT / FAILURE PATTERN)
Source: temporalio/sdk-go `master` `internal/internal_task_handlers.go` (`matchReplayWithHistory`, `isCommandMatchEvent`).
- Replay compares the commands regenerated by current code to recorded history; mismatch → `"[TMPRL1100] nondeterministic workflow: missing replay command for %s"` / `"extra replay command"` / `"history event is %s, replay command is %s"`. Default `WorkflowPanicPolicy` is BlockWorkflow (task fails and retries, workflow stays open for a fix) vs FailWorkflow. Mitigations: `workflow.GetVersion` / `patched()` markers recorded in history, and server Worker Versioning (pinned vs auto-upgrade deployments) so a run finishes on the code it started with.
- Class: INVARIANT (code that interprets a history must be the code, or a declared-compatible version, that wrote it) + FAILURE PATTERN (silent code change mid-run corrupts the run).
- UWCP mapping: UWCP does not replay code, so non-determinism per se does not apply; the analogue is **mission revision / runtime-manifest drift between epochs**. **COVERED mostly**: baseline.py classes correctness drift → refuse unless a re-pin event (≈ pinned deployment + explicit patch marker); epoch.dispatching records provider identity. **PARTIAL G-T6**: pin the *mission revision* in `epoch.begin` and have the runner refuse if the brief it received names another revision; and the *judge* must evaluate against the revision the final epoch ran under, not the latest one. Test: re-pin mission revision while an epoch is RUNNING; its receipt ingests (recorded under old revision) but the next epoch's brief carries the new revision and the judge verdict names which revision it judged.

### T-LOCAL. What our own epoch.py already does (read 2026-09-25, working tree of this repo)
Read `modules/gsd_x/goal/epoch.py` lines 208-273 to avoid claiming gaps that are already closed:
- `begin()` mints `{"run_token": uuid4().hex, "epoch_id": ...}` BEFORE the effect and records `revision: state.revision` in the DISPATCHING event → mission revision IS pinned per epoch (G-T6 half-covered). Appends with `log.append(state.last_seq + 1, ...)` — a sequence-number CAS on the log (the local analogue of `PreviousRangeID`).
- `begin()` refuses only an open epoch with the **same info_key**; an open epoch with a *different* key does not block a new one. So "≤1 running run per goal" (Temporal's WorkflowID invariant, T5) is **NOT enforced** today. **Gap G-T5b.** Test: `begin(key=A)`, then `begin(key=B)` without `end` → must raise.
- `ingest_receipt()` refuses unknown epoch, duplicate receipt_id, and revision mismatch. It does **not** refuse a receipt for an epoch whose state is `ended` (the planned "ended-epoch refusal" is not implemented yet) and there is no fence field. Consistent with the spec's "EXTEND" label; confirms G-T3a is open.

### T7. Temporal failure corpus (FAILURE PATTERN)
All at github.com/temporalio/temporal, read via api.github.com 2026-09-25.
- **#9118 "Stuck activities when temporal crashes"** (opened 2026-01-22, v1.29.2, closed completed 2026-02-19). ActivityTaskScheduled written to history + transfer task written (one txn), then the transfer processor RPCs matching and deletes the transfer task; a crash before matching commits leaves the activity "Scheduled" in history with no task anywhere. Quote: "The gap is between step 2 and 3 - it's an RPC call, not transactional." Causal abstraction: **intent durably recorded, dispatch acknowledged-and-forgotten by the sender before the receiver made it durable** (outbox deleted on send, not on receiver commit). UWCP exposure: HIGH — `DISPATCHING` intent → `gex44_cli queue add` → dispatcher. If the reconciler treats a successful `queue add` as terminal and the dispatcher's queue file is not fsynced before ack, the same orphan appears. UWCP §14 has "probe by run_token" which covers it **only if the probe runs on every DISPATCHING-without-RUNNING epoch, periodically, not just after a home crash**. Test: make the dispatcher ack `queue add` then drop the job (kill -9 before write); assert the next sweep probes the run_token, finds nothing, and marks LOST(not_enqueued) within one sweep interval.
- **#4137 "Reject fast signals when workflow task is failing at continueAsNew"** (2023, closed completed 2023-08-10) and **#1289 "Do not fail continue as new on a new signal"** (2021, open). A run that must hand off is prevented from doing so because new inputs keep arriving and the server refuses to close a run with unread inputs → livelock toward history limits. Abstraction: **handoff requires a quiescent input set; unbounded input rate starves the handoff.** UWCP exposure: MEDIUM — operator events (pause/cancel/re-pin) arriving during an epoch's HANDOFF NOTE/capsule write. UWCP must define whether operator events arriving after the capsule is sealed belong to the next epoch (Temporal's option 3: carry buffered signals to the next run). Test: inject an operator.note every 100 ms during capsule seal; epoch must still end and the events must appear exactly once in the next epoch's brief.
- **#6638 "Workflow cannot be terminated"** (v2.19 cloud/UI; closed 2025-03-06): `"transaction size of 5074977 bytes exceeds limit of 4194304 bytes"` on UpdateWorkflowExecution during *terminate*. Abstraction: **the kill switch shares a size-limited write path with the thing it kills, so the object grew past the point where it can be stopped.** UWCP exposure: MEDIUM — cancel is a goal-log append + CAS; if any append path validates the whole projected state (e.g. brief byte bound refusal) the cancel must be exempt. Test: grow a goal until the brief bound refuses; assert `operator.cancel` still appends and dominates.
- **#4812 "Starting abandoned child after parent closes"** (closed 2023-08-26): child started just before parent closure never gets its first task and stays open forever. Abstraction: **a spawn racing with the owner's close creates an orphan with no owner to reap it.** UWCP exposure: epoch dispatched while the goal is being cancelled/CONVERGED. Test: cancel CAS and `begin` race; after both, either no DISPATCHING exists or it is ended CANCELLED by the next sweep.
- **#2683 "fails to create workflow with the same ID ... Scylla"** (2022): ownership-lost error loop at high CPU when the persistence backend's conditional write (LWT) semantics differ. Abstraction: **a fencing protocol is only as good as the store's CAS; a store with weaker conditional semantics turns fencing into a retry storm.** UWCP exposure: flock on the VPS is fine on local ext4, NOT on NFS/overlay — record the filesystem as a precondition. ## 2. ETCD

### E1. Lessor: grant / renew / revoke / expiry (ALGORITHM / INVARIANT)
Source: etcd v3.7.2 `server/lease/lessor.go`.
- Constants: `MaxLeaseTTL = 9000000000` (s); `defaultLeaseCheckpointInterval = 5 * time.Minute`; `defaultLeaseRevokeRate = 1000`; `leaseCheckpointRate = 1000`.
- Grant: `if l.ttl < le.minLeaseTTL { l.ttl = le.minLeaseTTL }` — a TTL below the floor is **silently raised**, not refused; `ErrLeaseExists` if the ID is taken (client-chosen IDs allowed; ID 0 = server assigns). minLeaseTTL is derived from the election timeout (server config), so no lease can be shorter than one leader failover.
- Revoke: one txn, `for _, key := range keys { txn.DeleteRange([]byte(key), nil) }` — **all keys attached to the lease are deleted atomically with the lease**; `ErrLeaseNotFound` otherwise. Expiry = revoke by the leader (expiry loop runs only `if isPrimary()`, pushes to `expiredC`), rate-limited by `defaultLeaseRevokeRate`.
- Renew (KeepAlive): `if !le.isPrimary() { return -1, ErrNotPrimary }` — only the leader renews; renew clears a checkpointed remainingTTL through a raft `LeaseCheckpointRequest`.
- Promote (new leader): every lease is refreshed with `extend` (≈ election timeout) and expiries are spread "so piled up leases don't consume the entire revoke limit". Checkpoint stores only `remainingTTL` ("Promote is responsible for applying this to lease expiry").
- Class: ALGORITHM (TTL owned by the authority, clock not replicated — expiry computed from local monotonic time on the current leader) + INVARIANT (lease death and deletion of everything it guards are one atomic step).
- UWCP mapping: **PARTIAL.** UWCP: single-authority flock store on the VPS (no leader change → the Promote problem mostly vanishes), holder-only renew (≈ ErrNotPrimary is not needed; holder check is the analogue), TTL from DISPATCH. Gaps: **G-E1a min-TTL floor** — nothing states a minimum lease TTL relative to the dispatcher's renew interval + a node round-trip; a TTL shorter than renew-interval + RTT expires healthy holders. etcd *raises* rather than refuses; for UWCP, refusing is better (explicit). **G-E1b restart = implicit extend**: when the VPS store restarts, does a lease's remaining TTL resume from a persisted expiry (wall clock) or restart from full? etcd's history (E2) shows both choices bite. **G-E1c atomic revoke of attached state**: when a lease expires, the dispatcher job/fence it guards must be invalidated in the same store transaction (fence bump on expiry), else an expired-but-running job keeps a valid fence. Tests: (1) grant with TTL < floor → refused with reason; (2) restart store mid-lease, assert expiry time unchanged (± clock) — never extended to full TTL; (3) expire a lease; in the same flock critical section the fence generation for that resource must be > the job's staged fence.

### E2. Lease TTL reset on leader change → LeaseCheckpoint (FAILURE PATTERN)
Sources: etcd issue **#9888** "Leases may be auto-renewed indefinitely due to leader elections" (opened 2018-06-26, closed 2018-07-24); fix PR **#9924** LeaseCheckpoint; tracking **#13776** "Track stabilization of lease checkpointing" (2022-03-10); flags moved to feature gates in PR **#19356** (2025-02-06); **PR #21372** (2026-02-26) "fsync WAL backup before truncate, check lease checkpoint error": "The error from raftRequestOnce is discarded and the checkpointer callback always returns nil. Failed raft proposals silently lose checkpoint data."
- Symptom (#9888): 1-hour Kubernetes event leases were never revoked because each leader election "extends timeouts automatically for all leases" — frequent elections ⇒ leases immortal ⇒ storage exhaustion.
- Root cause: remaining TTL was not replicated/persisted; a new owner of the clock re-derived expiry as *now + full TTL*. Checkpointing persists `remainingTTL` periodically (5 min) so a new leader resumes near the true expiry. Second-order bug (#21372): the checkpoint write's error was swallowed, so a failed checkpoint looked like a successful one.
- Causal abstraction: **when a timeout's clock owner changes, "restart the clock" is the safe-for-availability and unsafe-for-bounded-lifetime choice; a bounded lifetime needs the remaining budget persisted by the authority, and the persist must be checked.**
- UWCP exposure: MEDIUM. Any UWCP clock that is restarted by a restart of its owner (supervisor cron, dispatcher restart, VPS reboot) — lease TTL, epoch budget (45 min), stall deadline, `max_hours` — silently extends. Test: for each deadline, kill/restart its owner at 90% of the budget; assert the deadline fires at ≤ original_deadline + one sweep interval.

### E3. client/v3/concurrency Mutex and the fencing caveat (PROTOCOL PATTERN / INVARIANT)
Sources: etcd v3.7.2 `client/v3/concurrency/mutex.go`; Jepsen "etcd 3.4.3" (jepsen.io/analyses/etcd-3.4.3, published 2020-01-30); etcd issue **#11456** "Locks return without checking whether the lease is still held" (2019-12-16, fix PR **#11408**).
- Mutex = `{s *Session, pfx, myKey, myRev, hdr}`; `myKey = pfx + leaseID`. `tryAcquire` txn: `If(CreateRevision(myKey) == 0) Then(Put(myKey, "", WithLease(s.Lease())), Get(pfx, WithFirstCreate())) Else(Get(myKey))` — ordering is by **CreateRevision**; the oldest waiter holds the lock. `Lock` then `waitDeletes(ctx, client, pfx, myRev-1)` (wait for every key with a smaller create revision to be deleted) and finally re-checks that its own key still exists, returning `ErrSessionExpired` if not (this is the #11456 fix; before it, a client whose lease expired while waiting returned from Lock believing it held the lock).
- `IsOwner()` returns `Compare(CreateRevision(myKey), "=", myRev)` — a **guard to embed in the protected write's Txn**, so a write by a deposed holder fails atomically. This is the only safe use.
- Jepsen: "multiple clients may hold the same etcd lock simultaneously. While this problem is exacerbated by process pauses, crashes, or network partitions, it can also occur in healthy clusters." With 1-3 s TTLs and pauses every 5 s, ≈18 % of acknowledged updates were lost in a lock-protected set. Recommendation: "every interaction with the shared resource includes a monotonic fencing token—for instance, the etcd revision associated with the currently-held lock key."
- Class: PROTOCOL PATTERN (lock = liveness hint; fence = safety) + INVARIANT (mutual exclusion is only guaranteed where the resource checks the token) + FAILURE PATTERN (re-check lease after any wait).
- UWCP mapping: **PARTIAL — this is the most important finding.** UWCP's resources guarded by the lease are (a) the goal log at the home (checks fence at ingest ⇒ SAFE), (b) the Dolphin slot / GPU VRAM / ksr_workspace on the node, and (c) the git remote / artifact store. (b) and (c) **do not check a token**: two runners believing they hold `dolphin_slot` (process pause on GEX44 past TTL, dispatcher renews for a new holder) will both drive Dolphin. **G-E3 resource-side fencing absent for node-local resources.** Cheap fixes: the runner writes `fence` into a node-local lockfile under `flock` *on the node* and every side-effecting call re-reads it (the resource then "checks the token" locally); git pushes go to fence-named refs. Also **G-E3b wait-then-recheck**: after any wait (queue, `waitDeletes` analogue = waiting in the dispatcher queue), the runner must re-read the lease/fence before its first effect — UWCP §9 says "dispatcher re-checks at dispatch" ✔ and "runner verifies before each side effect" ✔ — COVERED on paper; falsify with: SIGSTOP the runner for TTL+1 s after its pre-check, grant the lease to a second job, SIGCONT; assert the first runner's next effect is refused and the node lockfile shows only the second fence.

### E4. Txn CAS on revisions; watch revision + compaction (DATA MODEL / PROTOCOL PATTERN)
Sources: etcd v3.7.2 `client/v3/watch.go`; mutex.go (above) for Txn usage.
- Every key has `CreateRevision` (revision of the creating put; 0 = absent), `ModRevision` (last put), `Version` (puts since creation, reset on delete), and the store has one global monotonic `Revision`. Txn = `If(compares...) Then(ops) Else(ops)`, all atomic. CAS idioms: create-if-absent `CreateRevision==0`; update-if-unchanged `ModRevision==seen`; still-mine `CreateRevision==myRev` (Jepsen's variant: `Version > 0`).
- Watch: `WatchResponse{Header, Events, CompactRevision ("the minimum revision the watcher may receive"), Canceled, Created}`; `Err()` → `ErrCompacted` when `CompactRevision != 0`, `ErrFutureRev` when canceled without reason. On compaction past the watcher's start, "the watch will be canceled by the server, the client will post a compacted error watch response, and the channel will close" — the client must **re-list (Get at a revision) and re-watch from that revision+1**; it cannot recover the gap. `IsProgressNotify()` = empty response with non-zero revision (a bookmark: "nothing happened up to rev R"). Jepsen: watch at revision 0 starts at current+1, not at the first revision.
- Class: DATA MODEL (per-key create/mod/version + global revision) + PROTOCOL PATTERN (gap is an explicit error, never a silent skip; bookmark distinguishes quiet from lost).
- UWCP mapping: goal log `seq` ≈ global revision; `log.append(state.last_seq+1, …)` ≈ `ModRevision==seen` CAS → **COVERED** for the log. **PARTIAL G-E4 consumer resume**: any consumer that tails the goal log (status view, supervisor, KSR projection of AUTHORIZED/CONSUMED) needs "resume from seq N" and a *refusal* if N was compacted/retained away (capsule retention = "keep last N" ⇒ a compacted-capsule analogue exists). Also progress-notify ≈ UWCP heartbeat "missed != quiet" ✔ COVERED. Test: ask the capsule store for a capsule outside retention → explicit `COMPACTED` outcome, never an empty/UNKNOWN that a caller may read as "no capsule".

### E5. etcd failure corpus (FAILURE PATTERN) + robustness harness (TEST PATTERN)
Source: etcd v3.7.2 `tests/robustness/README.md` (bug table + watch guarantees); individual issues via api.github.com.
- **#14370 "Durability API guarantee broken in single node cluster"** (closed 2022-09-22): the API thread acknowledged a put before the batcher flushed to WAL; crash in between lost an acked write — "the kv is neither written to wal nor to database file". Abstraction: **ack precedes durability.** UWCP exposure: HIGH for a single-authority home — `goal/log.py` appends with fsync + dir fsync (spec §4), so COVERED *if* the forced-command verb returns only after both fsyncs; the dispatcher's queue file (not under UWCP control, S5a brings it under VCS) is the likely violator. Test: fault-inject crash (kill -9) after each syscall of `append` and of `queue add`; after restart every acknowledged event/job is present.
- **#11456** (lock returned without lease re-check) — see E3.
- **#9888 / #21372** (lease immortal after elections; checkpoint errors swallowed) — see E2.
- **#15271 "Watch traveling backward after network partition"** (2023) and **#17529 "Watch events lost during stream starvation"** (2024), **#18089 "Watch event loss during compaction deletion"** (2024), **#17247 duplicated watch events (TXN caching)** (2024). Abstraction: **a change feed's ordering/uniqueness/completeness are separate guarantees, each broken independently in production.** UWCP exposure: LOW-MEDIUM (the goal log is read by replay, not by a feed; the dispatcher's collect/job-peek is a feed). Test: harvest the same collect dir twice and out of order → exactly one receipt ingested (dedup by receipt_id ✔ in `ingest_receipt`).
- **#10681 "prevKV not returned if previous compacted"** (open since 2019): a delete event loses its previous value when compaction intervenes. Abstraction: **evidence needed to interpret an event can be garbage-collected before the event is consumed.** UWCP exposure: capsule retention "keep last N receipted" vs a harvest/judge that needs an older capsule. Test: judge a goal whose final receipt references a capsule already rotated out → refused with named reason, never judged against a newer capsule.
- **#20418 "Stale reads from process pausing"** (2025, Antithesis). Same class as Jepsen pause findings → reinforces G-E3.
- TEST PATTERN: etcd's robustness suite = traffic generator + failpoint injection (partitions, crashes, disk faults) + full client-history recording + **Porcupine linearizability check** + named watch guarantees (Ordered, Unique, Atomic, Bookmarkable, Reliable, Resumable). Importable to UWCP as: record every (verb, args, response, t_start, t_end) from control surfaces + dispatcher during a chaos run, then check a sequential model of the goal state machine (dispatching→running→ended, one open epoch, fence monotone, cancel dominates). Porcupine is a Go library (license NOT verified in this pass); a Python model checker over a small history is an estimated ~150 lines.

## 4. TOP 10 IMPORTABLE INVARIANTS
1. **Fence checked atomically with the effect, not before it** (Temporal `readLockShard` inside `txExecuteShardLocked`). UWCP: only home ingest is atomic → node effects are provisional; external effects go to fence-named refs promoted by the home. [G-T2a]
2. **A deposed owner stops itself on the first stale-fence signal and never retries** (`stopReasonOwnershipLost`; `ShardOwnershipLostError` non-retryable). [G-T2b]
3. **A completion names the full attempt identity and all of it is compared** (run_id, scheduled_event_id, attempt, version) — fence alone is insufficient. [G-T3a]
4. **"Your token is stale" (drop) ≠ "my view is stale" (reload)** (`ErrActivityTaskNotFound` vs `ErrStaleState`). [G-T3b]
5. **≤1 running run per identity** ("never valid to have two actively running instances of the same workflow id"). UWCP `begin()` today blocks only same-info_key. [G-T5b]
6. **Idempotency keys return the prior outcome, and their scope must span the handoff** (Update dedup is per-run and is lost across Continue-As-New — do operator-event dedup per goal, not per epoch). [G-T5]
7. **Graded bounds: suggest < warn < error** (4 MiB / 10 MiB / 50 MiB history; 4k/10k/51k events) so a rollover is voluntary and early; apply to goal log size and capsule size. [G-T1]
8. **Four separate clocks: queue-wait, per-attempt, total, liveness** (ScheduleToStart/StartToClose/ScheduleToClose/Heartbeat); UWCP lacks a queue-wait bound for failover:never jobs. [G-T4]
9. **A clock whose owner restarts must resume from a persisted remaining budget, and the persist must be checked** (etcd #9888 → LeaseCheckpoint; #21372 swallowed checkpoint errors). [G-E1b/E2]
10. **Mutual exclusion exists only where the resource checks the token** (Jepsen etcd 3.4.3; `IsOwner()` = Cmp to embed in the guarded Txn); lease death must invalidate guarded state in the same transaction (etcd revoke deletes attached keys atomically). [G-E3, G-E1c]
