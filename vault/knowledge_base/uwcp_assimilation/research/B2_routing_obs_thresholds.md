## 1. LiteLLM (BerriAI/litellm)

Ref: main @ `c19ce71bcdad234ca87a7af10cee45375ce811a8` (2026-09-25T07:48:42Z); latest release `v1.102.1` (2026-09-23); pyproject on main says `1.104.0`.

### 1.1 Cooldown (router_utils/cooldown_handlers.py, constants.py)
- `_set_cooldown_deployments(router, original_exception, exception_status, deployment, time_to_cooldown, requested_model_group) -> bool`: runs `_should_run_cooldown_logic()` then `_should_cooldown_deployment()`; if true, adds deployment to the cooldown list + callback.
- Status classification (quoted comments): 429 "Cool down 429 Rate Limit Errors"; 401 "Cool down 401 Auth Errors"; 408/404 cool down; "Do NOT cool down all other 4XX Errors"; 5XX and others cool down.
- Base case without `allowed_fails_policy`: `percent_fails = fails/(successes+fails)` in the current minute; cool down iff `percent_fails > DEFAULT_FAILURE_THRESHOLD_PERCENT and total_requests_this_minute >= DEFAULT_FAILURE_THRESHOLD_MINIMUM_REQUESTS and not is_single_deployment_model_group`. Single-deployment groups: "by default we should avoid cooldowns on single deployment model groups" (only 100 % failure at >= `SINGLE_DEPLOYMENT_TRAFFIC_FAILURE_THRESHOLD` cools one).
- Constants (constants.py): `DEFAULT_COOLDOWN_TIME_SECONDS=5`, `DEFAULT_FAILURE_THRESHOLD_PERCENT=0.5`, `DEFAULT_FAILURE_THRESHOLD_MINIMUM_REQUESTS=5`, `SINGLE_DEPLOYMENT_TRAFFIC_FAILURE_THRESHOLD=1000`, `DEFAULT_MAX_RETRIES=2`, `DEFAULT_ALLOWED_FAILS=3`, `ROUTER_MAX_FALLBACKS=5`.
- `allowed_fails_policy` is per exception class (`BadRequestErrorAllowedFails`, `AuthenticationErrorAllowedFails`, `TimeoutErrorAllowedFails`, `RateLimitErrorAllowedFails`, `ContentPolicyViolationErrorAllowedFails`, `InternalServerErrorAllowedFails`, `ServiceUnavailableErrorAllowedFails`, `BadGatewayErrorAllowedFails`, `NotFoundErrorAllowedFails`); counter is a fleet-wide cache key, cool down when `updated_fails > allowed_fails`.

**Classification / UWCP mapping**
- ALGORITHM (rate-based cooldown with a minimum-sample floor) — **REJECTED for UWCP as-is**: UWCP runs ~4-6 epochs/day per provider; a per-minute percentage with a floor of 5 requests can never fire at epoch cardinality. The *floor* is the invariant worth keeping: never judge a rate from fewer than N samples. UWCP analogue already exists: "2 same-signature failures -> provider_change" (count-based, which is correct for low cardinality). Mapping: covered. Falsification: feed the router 1 failure of signature S then 1 success then 1 failure of S — must NOT force a change if the rule is "2 consecutive"; decide and pin whether "2" means consecutive or cumulative (spec is silent). -> **gap (ambiguity)**.
- INVARIANT (cooldown keyed per deployment, not per model group) — UWCP: per (obligation, provider) failure signature; availability per provider. Partial: there is no *time-bounded* cooldown record with `until` — an UNAVAILABLE provider stays unselected until availability is re-measured (`measured_at` stale = unknown). That is stricter and fine. Falsification: mark qwen-local UNAVAILABLE at t0, re-probe OK at t1; the next epoch must select it only if `measured_at >= t1` and not before.
- FAILURE PATTERN (single-deployment exemption): LiteLLM refuses to cool down the *only* deployment because doing so turns a degraded group into a dead one. UWCP's chain always ends at a frontier rung, but the gate-first rung has no alternative. Mapping: covered by design (gate has no fallback; its failure is BLOCKED, not routed).

### 1.2 Retry policy (router_utils/get_retry_from_policy.py)
Quoted: `_RETRIES_BY_EXCEPTION_TYPE = MappingProxyType({AuthenticationError: ..., Timeout: ..., RateLimitError: ..., ContentPolicyViolationError: ..., BadRequestError: ..., ServiceUnavailableError: ..., InternalServerError: ...})`, resolved by walking `type(exception).__mro__` most-specific first, with a 404-specific rule first, else `policy.DefaultRetries`.
- PROTOCOL PATTERN: **retry count is a function of the exception class, resolved most-specific-first**; unknown class -> default. For UWCP, the default must be 0 retries (non-retryable) — the keos_qwen positive-list doctrine: an unrecognised outcome is HARNESS_FAILED, never "retry and hope". Mapping: partial (outcome.py has the vocabulary; there is no retry-count table per outcome). Proposed table: OK 0 · TRUNCATED 0 on same provider (route to larger ctx or refuse) · UNAVAILABLE 0 on same provider this epoch (route away) · AUTH_FAILED 0 + alert · HARNESS_FAILED 0 + stop the chain (instrument broke; routing elsewhere proves nothing). Falsification: inject each outcome, assert the router never re-dispatches the same (obligation, provider) within the epoch.
- Note: in LiteLLM `ContextWindowExceededError` subclasses `BadRequestError`, so an MRO walk that finds no specific entry falls to `BadRequestErrorRetries` — the specificity ordering matters. UWCP mapping: TRUNCATED must be its own class, never folded into a generic "bad request" failure signature. Covered by outcome.py.

### 1.3 Fallbacks (router_utils/fallback_event_handlers.py; types/router.py)
Quoted: `if fallback_depth >= max_fallbacks: raise original_exception`; `fallback_depth = fallback_depth + 1`; `if attempt_key in attempted: continue` (attempted_targets per request chain). Group selection order: exact match -> stripped -> provider-prefixed -> generic `"*"`. Three lists: `fallbacks`, `context_window_fallbacks`, `content_policy_fallbacks` (types only expose the first two in RouterConfig in the fetched text). Routing strategies (`RoutingStrategy` enum): `least-busy`, `latency-based-routing`, `cost-based-routing`, `usage-based-routing`, `usage-based-routing-v2`, `provider-budget-routing` (+ default `simple-shuffle`, not in the enum).
- INVARIANT: **fallback chain is bounded by depth AND by a visited-set** (both needed: depth bounds cost; visited-set prevents A->B->A oscillation inside the bound). UWCP: the chain is a static ordered list, visited implicitly. Covered, provided the chain is walked forward only. Falsification: configure a chain whose provider_change rule could re-select an already-failed provider in the same epoch; assert refusal.
- INVARIANT: **the error class selects the fallback list** (context-window errors go to larger-context targets, not to the next generic rung). UWCP §7 maps harness context errors to TRUNCATED but the chain is single. Gap: a TRUNCATED on qwen-local@32k should skip `codex@qwen-local` (same 32k window) and go to a frontier rung, or refuse if the prompt exceeds every rung. Falsification: prompt measured at 40k tokens -> router must never select any qwen-local rung (pre-dispatch), and a TRUNCATED on one qwen rung must not select the other qwen rung.
- REJECTED: `simple-shuffle`, `least-busy`, `latency-based` — randomized or load-sensitive selection breaks the "routing decision is a pure function of recorded inputs" property that UWCP needs for provenance replay. `usage/cost/provider-budget` routing: concept only (budget as a routing input — already in §7).

### 1.5b Complexity router (litellm/router_strategy/complexity_router/README.md, main @ c19ce71)
Directory also holds `auto_router/`, `adaptive_router/`, `quality_router/`, `budget_limiter.py`, `tag_based_routing.py`. ### 1.6 Disposition: **REFERENCE-ONLY** (reject adopt/wrap)
Reasons: (1) UWCP providers are mostly CLI harnesses (`claude -p`, codex, claude-harness@qwen) — LiteLLM's unit of routing is an HTTP completion call, so the harnesses would be outside its router entirely; (2) its cooldown algorithm is rate-based per minute and cannot fire at 4-6 epochs/day; (3) its selection strategies are randomized/load-driven, contrary to replayable routing provenance; (4) dependency weight + 2026-03 supply-chain incident + the open budget-race corpus; (5) the only HTTP endpoint (llama-server :8081) is already OpenAI-compatible and needs no gateway. Copy the invariants, not the code: exception-class -> retry count (default 0), per-target cooldown with explicit expiry, fallback list selected by error class, depth bound + visited-set, and "never let a logging path own routing state".

### 2.1 Model memory arithmetic (Qwen3-Coder-30B-A3B-Instruct)
- config.json: `num_hidden_layers 48`, `num_key_value_heads 4`, `head_dim 128`, `num_experts 128`, `num_experts_per_tok 8`, `max_position_embeddings 262144`. Params 30,533,947,392.
- Weight sizes: official FP8 safetensors ~31.2 GB (F8_E4M3 29.9B + BF16 0.64B) — **does not fit 20 GB**. unsloth GGUF: Q3_K_M 14.71 GB, UD-Q3_K_XL 13.81 GB, IQ4_XS 16.38 GB, Q4_0 17.38 GB, UD-Q4_K_XL 17.67 GB, Q4_K_M 18.56 GB, Q5_K_M 21.73 GB, Q8_0 32.48 GB.
- KV cache (derived, not measured): 2 x 48 layers x 4 KV heads x 128 x 2 B = 98,304 B/token (96 KiB) at f16 -> **3.0 GiB per 32,768-token slot**; ~1.5 GiB with q8_0 KV. So one 32k slot + IQ4_XS ≈ 15.3 + 3.0 GiB ≈ 18.3 GiB before compute buffers; Q3_K_M + 32k ≈ 16.7 GiB. The measured "~3.5 GB free of 20 GB with Qwen resident" is consistent with a ~Q3/IQ4-class quant with one 32k slot, or a Q4 with some MoE layers on CPU (`--n-cpu-moe N`, llama.cpp README: "keep the Mixture of Experts (MoE) weights of the first N layers in the CPU"). **The resident quant is not known to this agent — the GGUF sha pinned in the §11 baseline is the authority.**
- PERFORMANCE PATTERN: the 32k ctx cap in §7 routing is a *VRAM* decision (each +32k slot = +3 GiB f16 KV), not a model limit (262k native). Consequence for routing: "prompt tokens vs 32k" is a host-capacity fact and must be read from the running server (`/slots` `n_ctx`, or `/props`), not from a constant. Falsification: restart llama-server with ctx 16384; the router must refuse a 20k-token prompt on qwen-local without a code change.

### 2.2 vLLM on this card
- `vllm/v1/worker/utils.py::request_memory` (quoted): `requested_memory = math.ceil(init_snapshot.total_memory * cache_config.gpu_memory_utilization)`; `if init_snapshot.free_memory < requested_memory: raise ValueError("Free memory on device ... on startup is less than desired GPU memory utilization ... - Meaning for GEX44: vLLM reserves `utilization x TOTAL` up front and refuses to start unless that much is FREE. With ~16-17 GB of 4-bit weights, utilization must be >= ~0.85 of 20 GB just to hold weights, which requires the co-resident services to hold < ~3 GB VRAM *and* llama-server to be stopped. It cannot share the card elastically: the reservation is static for the process lifetime.
- Quantization (docs/features/quantization/README.md table, Ada SM 8.9 column): AWQ ✅, GPTQ ✅, Marlin ✅, llm-compressor FP8 W8A8 ✅ (Ada is the first supported arch), bitsandbytes ✅, GGUF ✅. FP8 is *supported* on Ada but the FP8 checkpoint is 31 GB -> irrelevant at 20 GB. A 4-bit AWQ/GPTQ MoE checkpoint would be the only vLLM-viable format.
- REJECTED for GEX44 today.

### 2.6 Decision and threshold
**GEX44 today: llama.cpp llama-server, unchanged.** Reasons: only runtime that (a) runs GGUF natively and non-experimentally, (b) allocates what it needs rather than a static fraction of TOTAL checked against FREE, (c) supports MoE expert offload to CPU (`--n-cpu-moe`) to trade speed for VRAM on a shared card, (d) is a single binary (disk 93 %).
Threshold at which vLLM/SGLang becomes justified — ALL of:
1. **Dedicated GPU** (no co-resident CUDA process), so a static `gpu_memory_utilization`/`mem-fraction-static` reservation is acceptable — measured by `nvidia-smi --query-compute-apps` listing only the server.
2. **VRAM >= 48 GB** (fits the 31 GB FP8 checkpoint that Ada/Hopper run natively + a real KV pool), or >= 24 GB *and* a 4-bit AWQ/GPTQ MoE checkpoint validated on the frozen S6a tasks with no quality regression vs the resident GGUF.
3. **Concurrency demand**: sustained `llamacpp:requests_deferred > 0` or `n_busy_slots_per_decode` at slot count for a meaningful share of epoch time — i.e. >= 3-4 concurrent epochs routinely queued behind one slot. Below that, continuous batching / paged attention buys nothing; a single sequential epoch stream is llama.cpp's best case.
4. **Disk headroom** for a CUDA/torch stack (>= 20 GB free after install).
Measured by: `/metrics` scrape over a week of real epochs (requests_deferred time share), nvidia-smi compute-apps, df.

## 3. OpenTelemetry / W3C Trace Context

Refs: W3C Trace Context Recommendation (23 Nov 2021), w3.org/TR/trace-context; open-telemetry/opentelemetry-specification main `specification/context/env-carriers.md` (fetched 2026-09-25); gen-ai conventions **moved** out of `open-telemetry/semantic-conventions` (docs/gen-ai/gen-ai-spans.md is now a redirect notice) into `open-telemetry/semantic-conventions-genai` main `docs/gen-ai/gen-ai-spans.md` + `model/gen-ai/registry.yaml`; opentelemetry-collector-contrib main `exporter/fileexporter/README.md`.

### 3.1 traceparent format (W3C REC)
`version-trace-id-parent-id-trace-flags`; version 2HEXDIGLC (`00`; `ff` forbidden); trace-id 32HEXDIGLC, all-zero invalid; parent-id 16HEXDIGLC, all-zero invalid; trace-flags 2HEXDIGLC (only sampled bit defined). Invalid traceparent -> receiver "restart the trace" (new ids). tracestate <= 32 list members. Send lowercase; accept any case of the header name.
- PROTOCOL PATTERN / INVARIANT. UWCP mapping: **gap** — §16 has no correlation id; epochs are identified by `run_token`/`epoch_id` (format unknown to W3C). Cheap adoption: goal = trace (trace-id = 16 random bytes minted at declare, persisted in the goal log), epoch = span (span-id minted at `epoch.dispatching`), provider call = child span. `run_token` stays the idempotency key; trace-id is correlation only — **never an authority** (a trace-id collision or forgery must not be able to adopt a run). Falsification tests: (a) parser rejects all-zero ids, uppercase hex in the value, `ff` version, wrong lengths; (b) an invalid inherited TRACEPARENT produces a NEW trace-id and a logged finding, never a crash and never reuse; (c) adopt-by-run_token works with TRACEPARENT absent.

### 3.2 Environment-variable carrier (OTel spec, env-carriers.md)
Status line quoted: "Status: Release Candidate". Key names are chosen by the propagator ("propagators that implement specific propagation formats (for example, W3C Trace Context or W3C Baggage) remain solely responsible for choosing the key names"), normalized by: uppercase ASCII letters; replace every char not `[A-Za-z0-9_]` with `_`; prefix `_` if starting with a digit (`^[A-Z_][A-Z0-9_]*$`) — so W3C `traceparent`/`tracestate`/`baggage` -> `TRACEPARENT`/`TRACESTATE`/`BAGGAGE`. Quoted rules: "Child-process startup is the point where context is extracted from environment variables"; "Applications avoid modifying context-related environment variables in the environment in which the parent process exists"; "Language implementations MUST NOT spawn child processes as part of environment variable context propagation". Security: "not appropriate for sensitive information"; env vars are readable by all code in the process.
- PROTOCOL PATTERN — exactly the boundary UWCP has (dispatcher -> runner -> `claude -p`/codex subprocess -> hooks). Mapping: gap, cheap: set `TRACEPARENT` in the child env at `Popen` (claude.py already injects `GSDX_GOAL_EPOCH` the same way). Hooks and the runner read it; nothing reads it for authority. Falsification: spawn a stand-in provider, assert it sees `TRACEPARENT` whose trace-id equals the goal's and whose parent-id equals the epoch span; assert the parent process's own `os.environ` is unchanged afterwards (spec rule).
- Across ssh the env var does not travel by default (sshd `AcceptEnv`); UWCP forced-command verbs should carry trace context as an explicit argument/field of `uwcp.control/1`, then re-export as `TRACEPARENT` on the node. Falsification: a job enqueued via `gex44_cli queue add` carries the trace-id in the job record and the node's receipt echoes it.

### 3.4 Collector file exporter (collector-contrib, exporter/fileexporter/README.md)
Stability: traces/metrics/logs **alpha**. "When `format` is json and `compression` is none, telemetry data is written to file in JSON format. Each line in the file is a JSON object." Rotation `max_megabytes` 100, `max_backups` 100, `max_days` unlimited, `localtime` false (UTC). Readback via the OTLP JSON file receiver.
- DEPENDENCY CANDIDATE -> **deferred**. The shape to copy now: one JSON object per line, UTC, size-bounded rotation. UWCP events can be written in a *subset* of OTLP JSON span shape (traceId, spanId, parentSpanId, name, startTimeUnixNano, endTimeUnixNano, attributes[]) so a future Collector's `otlpjsonfile` receiver can ingest them without a translation layer — but that conformance is optional; the goal log remains the authority.

### 3.5 Minimum viable contract + Collector threshold (summary; full contract in the section below)
No SDK, no Collector initially. Threshold to add a Collector (any one): (1) >= 3 hosts emitting epoch events that a human needs on one timeline and the pulled-JSONL merge by trace-id is a recurring manual step; (2) a consumer that needs push/alerting (e.g. p95 epoch latency SLO paging) — the file is pull-only; (3) event volume where per-epoch JSONL pull exceeds ~100 MB/day (rotation becomes the problem the exporter already solves); (4) a third-party backend (Tempo/Jaeger) is actually chosen. Measured by: count of distinct `host.id` in a week's events; bytes/day of event files; existence of a named consumer.
- ANTI-PATTERN (name it): **"Telemetry as a second ledger"** — the trace store starts answering questions the goal log owns (is the epoch done? which provider ran? how much budget is left?), then diverges (sampling, dropped spans, exporter backpressure, clock skew) and someone reconciles the log *to* the traces. Also its LiteLLM instance (#32574): routing correctness coupled to the logging path. Rule: telemetry is derived, lossy, and write-only from UWCP's point of view; no UWCP decision reads it. Falsification: delete every telemetry file / disable emission; `status`, routing and harvest outputs for a replayed goal must be byte-identical.

### 5.1 NATS JetStream (nats-io/nats.docs master: nats-concepts/jetstream/consumers.md, streams.md; fetched 2026-09-25)

## PROVIDER ROUTING DECISION RECORD (recommended fields)
One record per epoch, written into `epoch.dispatching` BEFORE the side effect, immutable; the decision must be a pure function of the record's inputs (replayable).

- `obligation_class`; `prompt_tokens_measured` + `tokenizer` + `measured_at`; `brief_tokens`.
- `candidates[]` in chain order, each: `provider` (e.g. `claude-harness@qwen-local`), `gen_ai_provider_name`, `model_id` + artifact identity (GGUF sha / CLI version), `ctx_window` **read from the live server** + `ctx_measured_at`, `availability` ∈ {AVAILABLE, UNAVAILABLE, UNKNOWN} + `availability_measured_at` + `availability_source` (/health, /slots, auth probe), `budget` {`ledger`, `used`, `cap`, `reservation_id` or null}, `prior` (benchmark row id + score), `failure_signatures_recent` (last 2 for this obligation), `feasible` + `refusal_reason` (named predicate: over_ctx, stale_availability, budget_spent, auth_failed, same_signature_twice, visited_this_epoch, ...).
- `selected` (provider or null), `selection_rule` (`first_feasible_in_chain`), `fallback_depth`, `visited[]`.
- `outcome` (append-only sibling record at harvest): keos_qwen outcome + AUTH_FAILED, `reason`, `retry_count` (expected 0), `timings` (TTFT/TPOT when available), `gen_ai.usage.input_tokens/output_tokens` when reported, raw `finish_reason` / exit code.

## MINIMUM VIABLE OBSERVABILITY CONTRACT
1. **IDs**: W3C formats only. trace-id (32 lowercase hex, non-zero, CSPRNG) minted at goal declare, persisted in the goal log; span-id (16 hex) per epoch and per provider call; `parent_span_id` links. `run_token` stays the idempotency/authority key; trace ids are correlation only and never authorize anything.
2. **Propagation**: `TRACEPARENT` (optional `TRACESTATE`) set in the child env at every subprocess spawn (runner, `claude -p`, codex, hooks); across ssh/queue the context is an explicit field of the `uwcp.control/1` verb / job record, re-exported on the node. Invalid inherited value -> new trace + finding.
3. **Events**: append-only JSONL, one object per line, UTC ns timestamps: `trace_id, span_id, parent_span_id, name, start_ns, end_ns, host_id, attributes{}`; attribute keys limited to pinned `gen_ai.*` names (operation.name, provider.name, request.model, response.model, response.finish_reasons, usage.input_tokens, usage.output_tokens, conversation.id), `error.type` only for genuine errors, and `uwcp.*` (outcome, obligation, rung, budget.*, lease.*, capsule.verdict). Keep the shape a subset of OTLP JSON span fields so a Collector's otlpjsonfile receiver could ingest later.
4. **No SDK, no Collector, no network exporter.** Emission is best-effort; failing to emit never blocks or alters work; one counter records emission failures.
5. **Authority rule**: no UWCP decision (routing, status, harvest, done-gate) reads telemetry. The goal log is the only source of truth. Test: telemetry removed -> byte-identical decisions.
6. **Server metrics**: llama-server `timings` copied into attempt evidence; `/metrics` scrape optional, only for the §2.6 threshold.
7. **Collector threshold**: >= 3 emitting hosts needing one timeline, OR a push/alerting consumer, OR > ~100 MB/day of events, OR a chosen backend.
