### 1\. El cambio fundamental: Scope como contrato de responsabilidad

El principio de KSEIP se puede universalizar porque no depende de Minecraft.

Un software puede ser una API, una biblioteca, un compilador, un agente, un videojuego, un sistema operativo, un modelo de IA, una migración o una herramienta de infraestructura.

Todos tienen algo en común:

Existen para producir resultados bajo determinadas condiciones, utilizando recursos y asumiendo obligaciones sobre sus efectos.

Por eso definiría scope así:

> Universal Software Scope = conjunto mínimo causalmente suficiente de responsabilidades necesarias para entregar, verificar, operar, mantener y evolucionar los resultados prometidos por un sistema, bajo sus restricciones y condiciones de uso.

Esto genera una distinción fundamental entre lo que el software debe conseguir y lo que debemos implementar para conseguirlo.

El scope no sería una lista de funcionalidades.

Sería un grafo semántico de obligaciones, relaciones causales, autoridad y evidencia.

### Los planos universales

| Plano                 | Responsabilidad                                            |
| --------------------- | ---------------------------------------------------------- |
| Product / Outcome     | Qué resultados promete el sistema                          |
| Capability            | Qué comportamientos deben existir                          |
| Architecture          | Qué contratos y componentes deben colaborar                |
| Ownership             | Quién posee, consume, modifica y verifica cada cosa        |
| Estate                | Qué infraestructura y recursos participan realmente        |
| State / Data          | Qué información existe, persiste, se comparte o elimina    |
| Operations / Recovery | Qué debe poder diagnosticarse, repararse y recuperar       |
| Verification          | Qué evidencia demuestra que funciona                       |
| Evolution             | Qué compatibilidad, migración y retirada debemos preservar |

Estos planos son independientes.

Por ejemplo, en un SaaS con pagos, el procesador de pagos puede quedar fuera de nuestro ownership y de nuestro implementation scope, pero dentro de nuestro dependency scope, verification scope y recovery scope.

Esto evita uno de los errores más comunes en ingeniería asistida por IA:

Confundir no poseer una dependencia con no ser responsable de las consecuencias de utilizarla.

Y también evita el contrario: apropiarse de funcionalidades que deberían pertenecer a una plataforma compartida.

### 2\. Universal Scope IR: el lenguaje que permitiría razonar sobre cualquier software

Este sería el primer gran componente técnico.

No crearía un segundo Knowledge Graph. Ampliaría la representación semántica canónica de Capability Runtime para incluir las responsabilidades y relaciones que determinan el scope.

Lo llamaría Universal Scope IR.

Cada obligación tendría una representación tipada, independiente del lenguaje de programación y del dominio.

| Campo          | Significado                                                         |
| -------------- | ------------------------------------------------------------------- |
| Identity       | Identidad semántica estable de la obligación                        |
| Origin         | Promesa, constraint, baseline o dependencia que la originó          |
| Applicability  | Condiciones bajo las cuales es obligatoria                          |
| Responsibility | Poseer, implementar, consumir, verificar, operar, recuperar, migrar |
| Subject        | Outcome, capability, recurso, dato, servicio o comportamiento       |
| Authority      | Fuente autorizada para establecer la obligación                     |
| Owner          | Sistema responsable de satisfacerla                                 |
| Context        | Runtime, producto, cohorte, versión y modo de operación             |
| Invariant      | Qué debe permanecer verdadero                                       |
| Evidence       | Qué observaciones sostienen la decisión                             |

| Lifecycle      | Cuándo aparece, cambia y deja de aplicar                            |
| Status         | Required, conditional, optional, forbidden, excluded o unresolved   |

No serían 14 campos obligatorios rellenados artificialmente en todas las operaciones. Serían un modelo semántico normalizado, con requisitos de información proporcionados a la importancia y riesgo de cada obligación.

### Aprendizaje retrospectivo: recuperar lo que CBR ya sabe

Antes de introducir nuevos baselines, ejecutaría una CBR Scope Knowledge Backfill.

Su finalidad sería recuperar de las fuentes institucionales existentes todo lo que ya puede informar decisiones de scope.

Por ejemplo, el Universal Scope Compiler debería consultar el conocimiento registrado sobre:

Cold Birth y reconstructabilidad: cuando un sistema necesita poder reproducirse desde estado declarado, esas obligaciones deben aparecer en scope desde el comienzo.

Canonical State Ownership: cuando múltiples componentes acceden a estado compartido, el scope debe resolver quién tiene autoridad para modificarlo.

Failure-to-Immunity: si un bug histórico nació porque una dependencia externa no se había considerado, ese mecanismo debe aparecer como detector en futuros proyectos aplicables.

False Locality: si un recurso aparentemente local modifica estado compartido, el scope debe reflejar sus efectos reales.

Production Reality: un artefacto construido pero no cargado, consumido o ejercitado no satisface el contrato de producto.

Context & Execution Reliability: los propios sistemas de captura y gobernanza tienen obligaciones de liveness, recuperación y observabilidad.

Una lección histórica puede ser útil aunque nunca haya sido formalmente etiquetada como una regla de scope. El proceso de backfill debe identificarla, vincularla a la evidencia original y proponer su interpretación semántica.

Pero no asumiría que todo conocimiento presente en archivos es automáticamente una baseline certificada.

Separaría conocimiento descubierto, conocimiento validado y conocimiento efectivamente promovido.

### La pieza nueva: Causal Transfer Contracts

Cada aprendizaje promovible tendría un contrato de transferencia.

Ese contrato respondería a estas cuestiones:

| Campo                 | Pregunta                                       |
| --------------------- | ---------------------------------------------- |
| Source mechanism      | ¿Qué fallo o necesidad explica el aprendizaje? |
| Preconditions         | ¿Qué debe ser verdad para aplicarlo?           |
| Guarantee             | ¿Qué mejora o propiedad ofrece?                |
| Exclusions            | ¿Cuándo sería incorrecto aplicarlo?            |
| Transfer evidence     | ¿Dónde se ha demostrado fuera del origen?      |
| Counterexamples       | ¿Qué contextos lo contradicen?                 |

| Invalidation          | ¿Qué cambio obliga a reevaluarlo?              |

Ésta sería la diferencia entre recordar patrones y poder reutilizarlos de manera segura.

Por ejemplo, el principio «todo recurso compartido debe tener una autoridad de escritura definida» puede transferirse ampliamente.

Pero la decisión «todo estado debe guardarse en Redis» no constituye un principio universal.

El primero describe una necesidad arquitectónica.

El segundo es una elección de implementación que podría perjudicar muchos productos.

### 6\. Scope Closure: cómo demostrar que el scope es suficientemente correcto

Aquí haría una distinción epistemológica importante.

No podemos demostrar en general que una descripción incompleta de un software contiene absolutamente todas las responsabilidades que surgirán en cualquier circunstancia futura.

Pero sí podemos exigir un certificado de cierre relativo a un contrato, un modelo, una cobertura y un horizonte explícitos.

El Scope Closure Gate comprobaría:

| Dimensión      | Condición de cierre                                                         |
| -------------- | --------------------------------------------------------------------------- |
| Product        | Las promesas y anti-goals materiales están identificados                    |
| Capabilities   | Las capacidades necesarias están derivadas y justificadas                   |
| Ownership      | No hay responsabilidades críticas huérfanas ni conflictos sin resolver      |
| State          | Recursos persistentes y transitorios tienen alcance y lifecycle             |
| Estate         | Las dependencias materiales se han examinado                                |
| Journeys       | Los recorridos críticos, incluidos los interrumpidos, tienen obligaciones   |
| Negative scope | Los estados prohibidos tienen controles o pruebas apropiadas                |
| Contingency    | Los fallos relevantes poseen respuestas explícitas                          |
| Verification   | Cada obligación crítica tiene un oracle adecuado                            |
| Evolution      | Cambios, migraciones, rollback y retirada están considerados cuando aplican |

La diferencia entre no aplicable y no examinado sería constitucional.

Una dimensión podría estar:

CLOSED, CONDITIONALLY CLOSED, NOT_APPLICABLE, UNKNOWN, BLOCKED o CONTRADICTED.

Y, de manera específica, un análisis no ejecutado conservaría el estado UNPRODUCED.

Esto aprovecha directamente el principio que ya estás utilizando en GSD X: la ausencia de una respuesta no puede convertirse en una respuesta negativa.

### Scope Closure no puede comprarse debilitando requisitos

El gate debería detectar cuando el agente intenta resolver un problema cambiando la definición del producto.

Ejemplos:

«No conseguimos que funcione reconnect; ahora reconnect está fuera del scope».

«La migración falla; declaramos que no soportamos usuarios antiguos».

«El benchmark no pasa; reducimos el objetivo».

Son modificaciones potencialmente legítimas solo si existe una decisión de producto o nueva evidencia que las autoriza.

No pueden producirse silenciosamente como mecanismo para conseguir un resultado verde.

### 7\. Scope Discovery debe ser bidireccional

El compilador necesita dos movimientos.

Expansión causal: descubrir qué responsabilidades adicionales son necesarias para satisfacer un resultado.

Contracción justificada: eliminar funcionalidades y dependencias que no aportan valor suficiente o que ya no son necesarias.

El primer movimiento resuelve under-scoping.

El segundo resuelve over-scoping.

Para ello utilizaría tres mecanismos complementarios.

### Causal Closure

Partiendo de cada outcome, recorrería dependencias y transiciones hasta que las obligaciones materiales estén satisfechas.

No debería expandirse infinitamente por todas las dependencias transitivas del sistema operativo o Internet.

La frontera estaría limitada por la materialidad del efecto, las condiciones de operación declaradas, la capacidad de control y la obligación real de verificación o recuperación.

### Counterfactual Scope Testing

El compilador preguntaría:

«Si quitamos este componente, ¿qué resultado deja de cumplirse?»

«Si se degrada, ¿qué promesa queda afectada?»

«Si cambia de propietario, ¿qué contratos aparecen?»

«Si sobrevive a una transición donde debería desaparecer, ¿qué invariantes rompe?»

Los experimentos de intervención aportarían evidencia más fuerte que una mera similitud textual, pero solo se ejecutarían en entornos y permisos apropiados.

### Minimal-Sufficient Pareto Search

En lugar de fabricar siempre el máximo scope, produciría alternativas con diferencias reales:

| Variante            | Objetivo                                                               |
| ------------------- | ---------------------------------------------------------------------- |
| Minimal Complete    | Mínima superficie que satisface las obligaciones del producto          |
| Professional Robust | Completitud más operabilidad, recuperación y verificabilidad adecuadas |
| Differentiated      | Innovaciones justificadas por la identidad y valor del producto        |
| Experimental        | Candidatos aislados que aún no pertenecen al contrato de producción    |

La palabra Professional no debería permitir que el compilador invente cientos de funcionalidades.

Un producto profesional es aquel cuya superficie comprometida está correctamente cerrada, no aquel que tiene más componentes.

### 8\. El scope tendría vida propia durante todo el desarrollo

No lo compilaría únicamente al empezar un proyecto.

Mantendría tres vistas versionadas de una misma realidad:

Product Scope Contract: las obligaciones vigentes del producto completo.

Mission Scope Delta: qué cambia realmente durante la misión actual.

Release Scope Contract: las obligaciones y estados que debe satisfacer una versión desplegable.

Esto es importante para evitar que cada tarea pequeña vuelva a analizar el proyecto entero.

El coste de compilación debe ser incremental, apoyado en cambios de dependencias, evidencia, código y baselines.

También sería dinámico.

Un recurso puede ser irrelevante durante funcionamiento normal y crítico durante una restauración. Una compatibilidad puede ser obligatoria solo para usuarios antiguos. Un servicio temporal puede dejar de ser necesario tras una migración certificada.

Por eso cada obligación podría tener condiciones de activación, expiración y reconsideración.

### Scope Mutation Governance

Cada cambio material generaría un evento semántico: expansión, contracción, transferencia de ownership, descubrimiento de dependencia, excepción temporal o retirada.

La modificación tendría que conservar el porqué, la autoridad, la evidencia y el impacto esperado.

El scope congelado de una release no podría modificarse silenciosamente para acomodar lo que terminó construyéndose.

Después de desplegar, Production Reality reconciliaría:

Desired Scope ↔ Constructed Scope ↔ Running Scope ↔ Experienced Scope.

Las divergencias materiales producirían Scope Drift o Scope Escape, no un simple cambio documental.

### 9\. El circuito de retroalimentación fuerte con CBR

Ésta sería la conexión institucional más valiosa.

1\. Universal Scope Compiler

Predice obligaciones y exclusiones antes de construir.

2\. Construction / Production Reality

Contrasta predicciones con construcción y comportamiento real.

3\. Scope Delta & Surprise Analysis

Clasifica omisiones, inclusiones innecesarias y errores de ownership.

4\. UCR-CIF + Knowledge Distillation

Extrae mecanismos, evidencias, contraejemplos y patrones reutilizables.

5\. CBR Promotion / Applicability

Promueve solo la madurez validada al alcance correcto.

6\. Future Scope Compilation

Una nueva misión recibe automáticamente los aprendizajes aplicables.

Pero añadiría una capacidad de segundo orden:

El compiler debe aprender qué preguntas de scope debería haber formulado y no formuló.

Supongamos que tres proyectos distintos sufren incidentes porque un servicio de analytics acaba siendo una dependencia crítica de operaciones principales.

No queremos almacenar simplemente tres notas sobre analytics.

Queremos abstraer la familia causal:

> Una dependencia observacional no debería convertirse accidentalmente en requisito de disponibilidad de una operación principal.

CBR puede entonces promover un detector condicional de criticality accidental.

La siguiente vez que el compiler construya una herramienta, un videojuego o un sistema distribuido, esa familia de riesgo entra en su análisis si se observan las precondiciones.

En sentido inverso, si la regla generara falsos positivos en sistemas donde analytics es explícitamente parte del producto principal, esos contraejemplos deben refinar el predicado.

Así el sistema no aprende acumulando prohibiciones indiscriminadas, sino mejorando la precisión de sus decisiones.

### Institutional Scope Return

Cada proyecto debería devolver al conocimiento institucional al menos una evaluación de:

| Resultado               | Aprendizaje                                          |
| ----------------------- | ---------------------------------------------------- |
| Anticipated correctly   | El compiler predijo la obligación antes de construir |
| Discovered during build | La obligación apareció tarde                         |
| Escaped to production   | La omisión llegó a producción                        |
| Unnecessary inclusion   | El compiler añadió scope sin justificación           |

No todos estos eventos necesitan una promoción.

Algunos deben terminar como evidencia local, otros como contraejemplos y algunos como mejoras de un detector existente.

La promoción únicamente estaría completa cuando una misión futura pudiera consumirla y demostrar una mejora real.

### I. La primera revolución: pasar de inferir funcionalidades a inferir obligaciones inevitables

La mayoría de agentes de programación trabajan mediante una lógica aproximadamente aditiva.

Reciben una petición, infieren funcionalidades plausibles, examinan el repositorio y proponen una implementación.

USCI debería trabajar de otra manera:

Partir de una promesa, derivar las condiciones necesarias para cumplirla y demostrar qué responsabilidades deben existir para mantenerla verdadera.

Eso requiere separar cuatro tipos de razonamiento.

| Tipo          | Pregunta que debe resolver                                              |
| ------------- | ----------------------------------------------------------------------- |
| Deductivo     | Dadas ciertas premisas, ¿qué obligaciones se siguen necesariamente?     |
| Abductivo     | ¿Qué capacidades podrían explicar o satisfacer el resultado solicitado? |
| Contrafactual | ¿Qué dejaría de funcionar si faltase algo?                              |
| Empírico      | ¿Qué demuestra el software, el entorno o un experimento real?           |

Esta separación es esencial.

Una deducción válida bajo un modelo no equivale a que sus premisas sean ciertas en producción. Una hipótesis plausible no equivale a una necesidad. Una correlación entre componentes no equivale automáticamente a dependencia causal.

USCI tendría que conservar esas diferencias durante toda la compilación.

### 1.1. Universal Obligation Calculus

La unidad fundamental del sistema no debería ser una feature, sino una obligación contextual.

Conceptualmente:

Obligación =

Precondiciones → Responsabilidad → Garantía → Evidencia

Siempre vinculada a autoridad, propietario, contexto, límites y condiciones de invalidez.

Un ejemplo:

«Si un sistema ejecuta operaciones externas que pueden repetirse, debe evitar que una repetición produzca efectos no autorizados».

No significa imponer indiscriminadamente idempotencia en toda función.

Significa examinar condiciones y seleccionar la protección apropiada.

| Composición detectada                      | Obligación derivada                                            |
| ------------------------------------------ | -------------------------------------------------------------- |
| Reintentos + cobros                        | Idempotencia efectiva o prevención equivalente del doble cobro |
| Multitenancy + caché                       | Aislamiento de claves, autoridad y contexto                    |
| Trabajos durables + reinicios              | Recuperación y tratamiento de ejecuciones duplicadas           |
| Agente autónomo + efectos irreversibles    | Límites explícitos de autoridad y controles proporcionados     |
| Estado temporal + persistencia global      | Política de transferencia y prohibición de contaminación       |
| Feature flags + migraciones                | Compatibilidad durante combinaciones intermedias autorizadas   |
| Datos replicados + escritores concurrentes | Contrato de consistencia y resolución de conflictos            |
| Servicio opcional + ruta crítica           | Justificación de criticality y política de degradación         |

La verdadera inteligencia está en inferir estas obligaciones a partir de la combinación, incluso cuando ninguna aparece literalmente en la petición.

Y el compiler también debe saber identificar cuándo no aplican.

Por ejemplo, una biblioteca puramente funcional, sin estado persistente ni efectos externos, no necesita inventarse una infraestructura distribuida de recuperación.

### 1.2. El espacio de scope deja de ser binario

Un elemento podría ser necesario para el producto, pero no pertenecer a su implementación.

Otro podría ser opcional durante funcionamiento normal y obligatorio durante recuperación.

Otro podría estar presente en la infraestructura, pero expresamente prohibido como dependencia de una operación crítica.

Por eso no usaría `in_scope = true/false` como representación primaria.

Cada elemento tendría una combinación de modalidad normativa y responsabilidad.

Las modalidades serían REQUIRED, CONDITIONAL, PERMITTED, OPTIONAL, FORBIDDEN, EXCLUDED y UNRESOLVED.

Las responsabilidades serían IMPLEMENT, PROVIDE, CONSUME, GOVERN, VERIFY, OPERATE, RECOVER, MIGRATE, OBSERVE y RETIRE.

Un servidor DNS, por ejemplo, podría ser CONSUMED y OBSERVED, sin ser IMPLEMENTED.

Una dependencia compartida podría ser GOVERNED contractualmente, sin que USCI reclamara su ownership.

Influencia causal no equivale a propiedad. Responsabilidad por un resultado no equivale a obligación de implementar todas sus dependencias.

Ésta sería una de las leyes más importantes del sistema.

### II. Universal Software Genome: aprender qué constituye cada clase de sistema

Aquí ampliaría directamente el Constitutive Baseline Ratchet.

CBR ya contempla algo fundamental en el dataset aportado: una capacidad nueva puede cambiar lo que significa construir correctamente una familia de sistemas.

También contempla herencia por instancia, familia, archetype, dominio y baseline universal; composición de capacidades y ratchet-on-touch.

La siguiente mejora sería representar esa madurez como un genoma constitutivo de software, no como una colección de features obligatorias.

Este genoma sería una proyección semántica de conocimiento existente, propiedad de Capability Runtime y CBR; no una segunda base de conocimiento.

### 2.1. Qué contendría un genoma constitutivo

| Elemento                  | Qué captura                                              |
| ------------------------- | -------------------------------------------------------- |
| Identity                  | Qué define esa clase de producto                         |
| Core outcomes             | Qué debe poder conseguir                                 |
| Constitutive capabilities | Capacidades cuya ausencia significa incompletitud        |
| Lifecycle grammar         | Cómo nace, funciona, se interrumpe y termina             |
| State laws                | Qué estado existe, quién lo posee y cómo cambia          |
| Composition laws          | Qué nuevas obligaciones aparecen al combinar capacidades |
| Forbidden worlds          | Estados y comportamientos inadmisibles                   |
| Environmental assumptions | Qué condiciones necesita del entorno                     |
| Operational guarantees    | Qué debe poder observarse y recuperarse                  |
| Proof obligations         | Cómo se demuestra cada propiedad                         |
| Applicability rules       | Cuándo debe heredarse                                    |
| Reversal conditions       | Cuándo una ley deja de ser aplicable                     |

La diferencia frente a un template sería radical.

Un template dice:

«Un motor de trabajos necesita estas diez piezas».

Un genoma constitutivo dice:

«Si el sistema tiene estas propiedades, entonces estas responsabilidades son necesarias; si carece de determinadas propiedades, otras no aplican».

### 2.2. Identidad por composición, no por etiquetas

El compiler no debería depender de reconocer perfectamente nombres comerciales o familias conocidas.

Debería poder descomponer una creación novedosa en estructuras causales reconocibles.

Por ejemplo:

PRODUCTO HIPOTÉTICO NO CONOCIDO

Un entorno colaborativo donde agentes programan, prueban y despliegan cambios.

Autonomous execution

Shared mutable state

Persistent workflows

Privileged actions

Concurrent actors

Human oversight

External dependencies

Versioned releases

Cada propiedad activa obligaciones propias. Sus interacciones generan obligaciones adicionales que ninguna propiedad individual explica por sí sola.

De ahí deberían derivarse automáticamente cuestiones como autorización de herramientas, aislamiento entre agentes, coordinación de escritores, protección del código existente, recuperación de trabajos, aprobación de acciones privilegiadas, trazabilidad y rollback.

Sin necesidad de tener previamente un template exacto llamado «Collaborative Agent Programming Environment».

Eso sería verdadera composición generativa de obligaciones.

### 2.3. Conditional Constitutive Genes

Ésta sería la unidad de madurez heredable más poderosa.

Cada gen codificaría:

Condición de activación → obligación → mecanismo causal → evidencia requerida → excepciones legítimas.

Ejemplo de gen:

Durable External Side Effect Safety

Se activa cuando una operación con efectos externos puede ejecutarse más de una vez debido a reintentos, reanudaciones, concurrencia o entrega duplicada.

Exige una estrategia que haga segura esa posibilidad, como idempotencia, deduplicación, transacciones adecuadas o compensación, dependiendo del efecto.

No exige una implementación concreta.

Y no se aplica si las precondiciones no existen.

CBR podría promoverlo desde una familia determinada hacia múltiples dominios cuando exista evidencia suficiente de transferencia.

### 2.4. El genoma también debería contener interacciones

Esto es especialmente importante.

Si A y B están presentes, puede aparecer C como obligación nueva.

El ejemplo clásico es reintentos más efectos no idempotentes.

Pero USCI debería aprender combinaciones de mayor orden.

Un sistema podría funcionar perfectamente con:

autonomía, permisos y recuperación.

Y aun así fallar al combinar:

autonomía × permisos revocados × reanudación de una operación antigua.

Ahora aparece una obligación sobre reevaluación de autoridad al reanudar.

Ésa no pertenece exclusivamente a «permisos» ni a «recovery».

Pertenece a la interacción.

Por tanto, el genoma debería contener relaciones causales de varios elementos, representables mediante hiperaristas o reglas composicionales.

La exploración debería estar priorizada por riesgo y evidencia; probar todas las combinaciones sería computacionalmente inviable.

### III. El verdadero motor: Causal Responsibility Hypergraph

La segunda gran innovación sería representar el scope como un hipergrafo dinámico de responsabilidad causal.

No lo almacenaría como otra copia completa del Knowledge Graph de CPP.

Utilizaría el grafo canónico existente y añadiría una representación compilada, versionada y orientada a decisiones.

### 3.1. Los objetos semánticos

El modelo necesitaría distinguir entidades como producto, actor, outcome, capability, operación, estado, recurso, servicio, contrato, dependencia, evento, versión, fallo, riesgo, obligación y evidencia.

Las relaciones más importantes serían:

| Relación       | Semántica                                                 |
| -------------- | --------------------------------------------------------- |
| REQUIRES       | Una obligación necesita otra condición                    |
| GUARANTEES     | Un componente promete una propiedad bajo ciertas premisas |
| ASSUMES        | Una garantía depende de una hipótesis externa             |
| CONSUMES       | Una capacidad utiliza un recurso o contrato               |
| MAY_MUTATE     | Existe autoridad para modificar                           |
| MAY_AFFECT     | Hay una consecuencia causal posible                       |
| MUST_NOT_REACH | Ciertos estados o efectos están prohibidos                |
| OWNED_BY       | Autoridad canónica                                        |
| VERIFIED_BY    | Evidencia que satisface la obligación                     |
| ACTIVATED_WHEN | Condición que hace aplicable la relación                  |
| INVALIDATED_BY | Evento que obliga a reevaluarla                           |

### 3.2. Por qué un hipergrafo y no un grafo ordinario

Muchos problemas importantes no pertenecen a un componente ni a una pareja de componentes.

Aparecen por composición.

Por ejemplo, una operación puede ser correcta con permisos válidos, correcta con reintentos y correcta con jobs persistentes, pero incorrecta cuando se reanuda después de que los permisos hayan expirado.

Una relación que depende de tres condiciones no debería reducirse artificialmente a tres dependencias binarias independientes.

El hipergrafo permitiría representar esa interacción como una obligación única y comprobable.

### 3.3. Causalidad con condiciones operativas

El grafo cambiaría según versión, cohorte, modo de operación y estado.

Una obligación podría activarse únicamente durante una migración, una caída de proveedor o el primer acceso de un usuario antiguo.

Por tanto, su universo de referencia no sería «los archivos presentes ahora».

Sería el conjunto de estados y transiciones relevantes dentro de un horizonte operativo definido.

Eso captura latent scope, contingency scope y obligaciones que solamente existen en escenarios excepcionales.

### 3.4. Compositional Assurance Contracts

Hay una base sólida en ingeniería formal para razonar de esta manera: los contratos assume-guarantee permiten estudiar garantías de componentes bajo supuestos explícitos, en lugar de verificar necesariamente todo el sistema como un bloque monolítico. El SEI de Carnegie Mellon ha investigado además arquitecturas de aseguramiento que combinan evidencias de subsistemas con diferentes niveles de confianza.

La aplicación concreta en USCI sería:

Un proveedor declara qué garantiza.

Un consumidor declara qué necesita.

El compiler comprueba si las condiciones encajan.

Si no encajan, produce una obligación de adaptación, una incertidumbre o un conflicto.

No debería rellenar silenciosamente el vacío entre dos contratos incompatibles.

Y el hecho de que los contratos encajen a nivel semántico no demostraría por sí solo que sus implementaciones reales sean correctas: esa afirmación exige evidencia adicional.

### IV. Scope como problema de síntesis de sistemas, no de enumeración

Esta es una mejora especialmente potente respecto al Universal Scope Compiler anterior.

USCI no debería generar un único scope y después revisar si está bien.

Debería razonar sobre un espacio de arquitecturas y responsabilidades posibles.

### 4.1. Separar el mundo de producto del mundo de implementación

Primero debe saber qué resultados forman parte del producto.

Después debe determinar qué capabilities satisfacen esos resultados.

Y solamente después debe estudiar qué arquitecturas permiten implementarlas.

Dos soluciones pueden cumplir el mismo contrato de producto con arquitecturas diferentes.

Por ejemplo, un sistema de eventos durables podría utilizar distintas tecnologías de persistencia.

El contrato puede exigir durabilidad, procesamiento seguro y recuperación, sin tener que exigir Redis, PostgreSQL o una cola determinada.

### 4.2. Scope como optimización bajo restricciones

La formulación conceptual sería:

\\begin{aligned}
\\text{Elegir un } S \\text{ que satisfaga:}\\quad
&\\text{Outcomes requeridos}\\\\
&\\text{Invariantes y prohibiciones}\\\\
&\\text{Responsabilidades de seguridad}\\\\
&\\text{Contratos de operación y recuperación}\\\\
&\\text{Obligaciones de evidencia}\\\\
\\\\
\\text{Y optimizar:}\\quad
&\\text{Complejidad, coste, riesgo y mantenibilidad}
\\end{aligned}

No existe necesariamente una única solución óptima.

Por eso utilizaría búsqueda de soluciones no dominadas, con restricciones duras que no se pueden sacrificar para mejorar una puntuación.

Las preferencias y tradeoffs legítimos de producto sí podrían producir varias alternativas.

### 4.3. Necessity versus Implementation Choice

Cada requisito tendría que responder a una pregunta:

¿Es realmente necesario para el resultado, o solamente se volvió necesario porque elegimos determinada arquitectura?

Esto crea una distinción:

Constitutive obligation: nace de lo que el producto debe hacer.

Architecture-induced obligation: nace de cómo decidimos construirlo.

Ejemplo:

El producto exige ejecutar tareas de manera durable.

Si elegimos una arquitectura distribuida, aparecen obligaciones adicionales sobre coordinación, consistencia y fallos parciales.

Esas obligaciones son reales, pero no deberían confundirse con nuevas funcionalidades de producto.

Esto permitiría que USCI comparase arquitecturas teniendo en cuenta el scope técnico que cada una induce.

### 4.4. Scope Fixed-Point Compilation

La síntesis funcionaría mediante aproximaciones sucesivas.

Primero deriva obligaciones directas.

Después incorpora obligaciones implícitas por dependencia y composición.

Luego descubre impactos en infraestructura, estado, operaciones y verificación.

Finalmente resuelve nuevas obligaciones inducidas por las decisiones arquitectónicas.

Este proceso continúa hasta alcanzar un punto estable dentro del modelo y del presupuesto de análisis.

Pero debe tener protección frente a expansión infinita, ciclos de reglas y dependencias irrelevantes.

El cierre es relativo a los supuestos y superficies explorados; no significa que un modelo finito haya descubierto todas las necesidades posibles de un sistema arbitrario.

Una extensión especialmente interesante sería utilizar abstraction refinement.

USCI empieza con una representación simple y refina solamente aquellas partes donde encuentra contradicciones, contraejemplos o incertidumbre material.

Así evita modelar exhaustivamente todo el universo de un producto antes de saber qué regiones son difíciles.

### V. La siguiente frontera: generar mundos donde el producto puede estar equivocado

Este sería uno de los mayores avances frente a un compiler convencional.

En lugar de limitarse a preguntar qué debe existir, USCI debería construir un espacio de mundos contrafactuales.

Cada mundo representa una variación relevante del funcionamiento del producto.

Por ejemplo, para un sistema que cobra suscripciones:

| Mundo       | Pregunta                                                                |
| ----------- | ----------------------------------------------------------------------- |
| Normal      | El cobro se procesa correctamente                                       |
| Duplicated  | El proveedor repite el webhook                                          |
| Interrupted | El proceso muere después de cobrar pero antes de registrar el resultado |
| Reordered   | Los eventos llegan fuera de orden                                       |
| Delayed     | La confirmación tarda más que el timeout                                |
| Revoked     | El usuario pierde autorización durante la operación                     |
| Migrated    | El esquema cambia mientras quedan trabajos antiguos                     |
| Degraded    | Un proveedor auxiliar deja de responder                                 |
| Restored    | Se reconstruye el sistema a partir de backup                            |
| Retired     | Se elimina la funcionalidad pero sobreviven datos o jobs antiguos       |

El compiler debe determinar qué propiedades cambian en cada mundo y qué obligaciones aparecen.

Esto es mucho más potente que añadir «manejar errores» como requisito genérico.

### 5.1. Counterexample-Guided Scope Refinement

El pipeline propuesto sería:

Contrato provisional

Modelo de actores, estados y transiciones

Generación de contraejemplos

¿Existe un incumplimiento alcanzable?

Nueva obligación o premisa corregida

Recompilación del scope

Esta lógica se inspira en técnicas de verificación y refinamiento de modelos.

Herramientas como TLA+ y su model checker TLC permiten explorar estados y detectar errores de diseño en modelos formales, particularmente en sistemas concurrentes y distribuidos. No significan, por sí solas, que se haya demostrado la corrección del programa de producción.

Para USCI usaría varios niveles de potencia:

Nivel ligero: generación de escenarios y pruebas de propiedades.

Nivel intermedio: modelos finitos de transiciones y contraejemplos ejecutables.

Nivel fuerte: model checking o razonamiento formal para protocolos y contratos críticos.

No haría que cada pequeño cambio de frontend pasase por verificación formal.

### 5.2. Illegal World Intelligence

El sistema debería aprender familias de estados imposibles.

Por ejemplo:

Un trabajo figura como CANCELLED pero sigue produciendo efectos.

Un usuario ha sido eliminado de un tenant pero conserva una sesión con autoridad antigua.

Una transacción aparece como COMMITTED en un servicio y ROLLED_BACK en otro sin contrato de compensación.

Un agente ejecuta una acción privilegiada después de revocarse su permiso.

Un componente retirado sigue siendo alcanzable mediante configuración heredada.

Éstos son defectos de scope porque revelan obligaciones de diseño que debieron inferirse antes de implementar.

Los modelos de estados prohibidos también deberían heredarse por CBR cuando son causalmente transferibles.

### 5.3. Negative Reachability Proof

Hay otro avance importante:

Demostrar que algo ya no puede suceder puede ser tan importante como demostrar que algo funciona.

Cuando retiramos una funcionalidad, USCI debería estudiar sus referencias, puntos de entrada, migraciones, recursos, configuraciones, schedulers, clientes antiguos y posibles rutas de reactivación.

Una retirada no estaría cerrada simplemente porque desaparece una clase o archivo.

Estaría cerrada cuando se hayan eliminado o gobernado los efectos relevantes y se disponga de evidencia adecuada de no alcanzabilidad.

La fuerza de esa evidencia depende del sistema: pruebas finitas, análisis estático, contratos de despliegue o comprobaciones de runtime.

Nunca debería afirmarse una imposibilidad absoluta basándose únicamente en que una prueba no reprodujo el comportamiento.

### VI. Scope Archaeology: que CPP reconstruya el scope de cualquier software existente

Aquí introduciría una capacidad que todavía no hemos desarrollado suficientemente: la compilación inversa del scope.

Hasta ahora hemos diseñado principalmente:

Intent → Scope → Architecture → Software.

Pero Claude Power Pack también debería poder hacer:

Existing Software → Observed Behavior → Inferred Contracts → Reconstructed Scope.

Esto es fundamental para aprovechar años de código preexistente y el conocimiento histórico anterior a USCI.

### 6.1. Universal Scope Archaeologist

Dado un repositorio y su entorno, debería reconstruir:

| Superficie           | Qué investiga                                  |
| -------------------- | ---------------------------------------------- |
| Entrypoints          | Cómo se activan funcionalidades                |
| Public interfaces    | Qué contratos reciben consumidores             |
| State writes         | Qué datos se modifican y bajo qué autoridad    |
| Dependencies         | Qué sistemas participan realmente              |
| Runtime effects      | Qué sucede fuera del código local              |
| Historical decisions | Por qué existe una arquitectura                |
| Tests                | Qué propiedades se consideran importantes      |
| Incidents            | Qué obligaciones se descubrieron tarde         |
| Deployment           | Qué hace falta para que el software funcione   |
| Operators            | Qué procedimientos humanos son necesarios      |
| Legacy paths         | Qué estados antiguos siguen siendo alcanzables |

La reconstrucción no debería confundir comportamiento actual con comportamiento correcto.

Un bug repetido durante cinco años no se convierte en una regla constitutiva por ser histórico.

Por tanto, el arqueólogo produciría dos grafos distintos:

Observed System Contract: lo que la evidencia indica que el sistema hace.

Intended Product Contract: lo que las decisiones autorizadas establecen que debe hacer.
Las divergencias serían materia prima extraordinariamente valiosa para USCI y CBR.

### 6.2. Una consecuencia importante

Imagina que encontramos un sistema antiguo que funciona solamente porque cierto procedimiento manual se ejecuta antes de cada deployment.

Un análisis tradicional podría concluir que ese procedimiento simplemente pertenece al proceso operativo.

USCI debería descubrir algo más profundo:

> Existe una precondición material para el correcto funcionamiento del producto que no está codificada ni verificada automáticamente.

Ese hallazgo puede producir una obligación de automatización, una mejora del contrato de operaciones o un nuevo baseline de reconstructabilidad.

Y después transferirse a otros proyectos con mecanismos causales equivalentes.

### VII. Scope Genetics: cómo convertir todo el aprendizaje histórico de CBR en inteligencia aplicable

Ésta sería una de las piezas con mayor retorno institucional.

El dataset UCR-CIF ya contiene las ideas de Knowledge Vault Writeback, UKDL Distillation, Constitutive Promotion Gate, familias de baseline, transferencia causal y aprendizaje de segundo y tercer orden.

USCI debería convertirlas en una cadena de capitalización semántica de scope.

### 7.1. Historical Scope Distillation

No me limitaría a incorporar los nuevos incidentes.

Ejecutaría una campaña retrospectiva sobre el conocimiento acumulado por CPP.

El objetivo sería identificar reglas de scope que ya fueron descubiertas, pero que nunca se registraron como tales.

Ejemplo:

En un proyecto se descubre que un proceso debe recuperar estado después de reiniciarse.

En otro se descubre que un comando necesita ownership verificable.

En otro se descubre que una capability existe pero ningún usuario puede alcanzarla.

En otro se descubre que una migración funciona en una máquina pero no desde cold birth.

Son incidentes distintos.

Sin embargo, pueden aportar mecanismos reutilizables sobre lifecycle, autoridad, reachability y reconstructabilidad.

La campaña debería producir candidatos vinculados a sus fuentes originales, no escribir automáticamente una nueva constitución.

### 7.2. Scope Mechanism Genome

Cada descubrimiento transferible debería conservar una estructura como ésta:

| Campo                   | Contenido                                       |
| ----------------------- | ----------------------------------------------- |
| Causal mechanism        | Qué relación explica el problema                |
| Origin evidence         | Qué experiencia produjo el descubrimiento       |
| Constitutive hypothesis | Qué obligación podría generalizarse             |
| Trigger predicate       | Cuándo debería aplicarse                        |
| Scope effect            | Qué responsabilidades añade, modifica o prohíbe |
| Known exceptions        | Contextos donde no aplica                       |
| Counterexamples         | Evidencias que debilitan la generalización      |
| Verification recipe     | Cómo comprobar la obligación                    |
| Transfer coverage       | En qué familias se ha validado                  |
| Baseline generation     | Qué versión de CBR lo incorpora                 |
| Invalidation events     | Qué cambios obligan a reconsiderarlo            |

El mecanismo de aprendizaje debe preservar causas y condiciones, no solamente resumir conclusiones.

Ésta es la diferencia entre una memoria útil y una fábrica de reglas sobreajustadas.

### 7.3. Scope Promotion Gate

Propondría la siguiente secuencia de estados:

1

OBSERVED

Se ha detectado un comportamiento o incidente

2

EXPLAINED

Existe una hipótesis causal respaldada

3

LOCAL VALIDATED

El mecanismo se ha comprobado en su contexto

4

TRANSFER CANDIDATE

Se propone aplicabilidad más amplia

5

CROSS-CONTEXT TESTED

Se prueban transferencias y contraejemplos

6

CONSTITUTIVE BASELINE

CBR acepta el alcance demostrado

7

INHERITED & MEASURED

Misiones posteriores lo consumen y validan

No todas las reglas tienen que alcanzar la universalidad.

Una norma muy valiosa puede permanecer como baseline de un archetype específico.

Y algunas propiedades podrían tener una justificación normativa o formal suficientemente fuerte sin necesitar diez incidentes empíricos.

CBR debe distinguir ambos casos.

### 7.4. El aprendizaje negativo debe tener el mismo valor

Supongamos que USCI aprende:

«Los sistemas con estado necesitan mecanismos de recuperación».

Más tarde intenta aplicarlo a una herramienta efímera cuya salida se puede recalcular de forma barata y donde no existe ninguna obligación de continuidad.

Si fuerza una infraestructura compleja de recovery, ha generalizado incorrectamente.

Eso debería generar un Applicability Counterexample.

CBR no solo aprende que recovery es importante.

Aprende cuándo lo es, qué garantía pretende satisfacer y cuándo una solución más simple cumple suficientemente el contrato.

En consecuencia, el sistema mejora tanto su recall como su precision.

### 7.5. La regla de no duplicación institucional

UCR-CIF seguiría siendo responsable de capturar y capitalizar las construcciones.

Knowledge Vault conservaría evidencia rica.

UKDL destilaría conocimiento.

CBR sería propietario de la promoción constitutiva.

UBC resolvería la herencia aplicable.

USCI consumiría esa herencia para compilar obligaciones y devolvería descubrimientos mediante esos mismos canales.

USCI no tendría un segundo ratchet, un segundo Knowledge Vault ni un segundo motor de gobernanza.

### VIII. Meta-Scope Intelligence: que mejore también el mecanismo que descubre scope

Éste sería el salto más profundo.

En el corpus UCR-CIF ya existe una idea de segundo y tercer orden:

No basta con acumular mejoras. El sistema debe mejorar su capacidad para descubrir, validar y transferir mejoras.

Aplicaría ese mismo principio al razonamiento de scope.

### Primer orden: aprender obligaciones

Un proyecto descubre que los reintentos pueden duplicar efectos externos.

CBR incorpora una obligación condicional.

Los siguientes sistemas aplicables la heredan.

### Segundo orden: aprender a descubrir obligaciones

USCI observa que sus omisiones aparecen frecuentemente cuando hay componentes con varios escritores.

En vez de añadir únicamente reglas individuales, mejora el detector que identifica recursos con autoridad de escritura ambigua.

Ese detector puede encontrar problemas nuevos que todavía no figuran en el corpus.

### Tercer orden: aprender qué investigaciones producen mayor información

Después de muchas misiones, USCI podría descubrir que, ante determinadas arquitecturas, analizar el lifecycle de los recursos revela más obligaciones críticas que inspeccionar listas de funcionalidades.

Su estrategia de exploración se ajustaría para invertir primero en las observaciones que mejor discriminan hipótesis.

Eso produce una capacidad nueva:

Scope Discovery Strategy Learning.

No solo aprende qué tiene que preguntar.

Aprende qué preguntas merece la pena investigar antes, qué evidencia distingue respuestas y cuándo detenerse.

### 8.1. Scope Research Policy

Cada campaña de investigación debería maximizar la información relevante para una decisión, teniendo en cuenta su coste y riesgo.

No gastaría grandes cantidades de tokens examinando una incertidumbre cosmética mientras permanece sin resolver quién tiene autoridad sobre una base de datos crítica.

El sistema debería priorizar preguntas con estas propiedades:

| Propiedad               | Motivo                                           |
| ----------------------- | ------------------------------------------------ |
| Decision relevance      | La respuesta cambia una decisión real            |
| Discriminating power    | La evidencia separa hipótesis competidoras       |
| Material consequence    | Un error tiene impacto significativo             |
| Uncertainty             | La respuesta todavía no está establecida         |
| Reuse potential         | El resultado puede mejorar futuras misiones      |
| Observation feasibility | Existe un instrumento adecuado para investigarla |

No todos estos factores necesitan expresarse como puntuaciones numéricas inventadas.

Pueden utilizarse clases ordinales y comparaciones justificadas.

### 8.2. Detector Ratchet

Cada omisión importante debe preguntarse:

«¿Qué detector habría podido descubrirla antes?»

Si existe conocimiento pertinente, pero no se recuperó, es un fallo de activación.

Si se recuperó, pero no se reconoció la aplicabilidad, es un fallo del resolver.

Si el conocimiento no existía, es un gap de investigación.

Si el detector lo señaló pero el gate lo ignoró, es un fallo de enforcement.

Si la prueba no podía observar el fallo, es un fallo de instrumentación.

Estas causas exigen soluciones distintas.

Un sistema que simplemente añade otra frase al prompt después de cada incidente no estaría aprendiendo de forma suficiente.

### 8.3. Meta-Ratchet con raíz de confianza independiente

La maquinaria que aprende también puede introducir errores.

Por tanto, una mejora del propio USCI no debería poder cambiar los criterios de evaluación y utilizar esos criterios recién modificados para certificarse.

Separaría conceptualmente:

Proposal Authority: puede crear hipótesis y mejoras.

Evaluation Authority: las prueba contra benchmarks y contratos previos.

Ratification Authority: decide la promoción.

Deployment Authority: aplica cambios de manera controlada.

Rollback Authority: restaura generaciones anteriores si aparecen regresiones.

Estos papeles pueden implementarse mediante componentes existentes y procesos independientes. No requieren necesariamente cinco servicios nuevos.

La separación es lógica y de autoridad.

### IX. Institutional Scope Experimentation Lab

Aquí iría más allá de revisar el scope con agentes críticos.

Crearía una disciplina de experimentación para descubrir obligaciones desconocidas.

No un laboratorio enorme desde el primer día, sino una capacidad progresiva dentro de la infraestructura de evaluación existente.

### 9.1. Hipótesis falsificables

Una decisión importante de scope debería poder expresar qué observación podría demostrar que es incorrecta.

Ejemplo:

«El sistema de analytics no puede afectar a la ejecución principal».

Contraejemplo buscado:

Una operación principal se bloquea cuando analytics deja de responder.

Si el contraejemplo aparece, debemos revisar el contrato de dependencias.

### 9.2. Perturbation experiments

En entornos autorizados, el sistema podría introducir fallos controlados.

Ejemplos: desconectar un proveedor opcional, duplicar un evento, retrasar un mensaje, reiniciar un worker, cargar un estado antiguo o modificar un feature flag.

El experimento debería tener un objetivo discriminante.

No ejecutar chaos testing indiscriminado.

### 9.3. Negative controls

Esto es fundamental para evitar conclusiones falsas.

Si un experimento pretende demostrar que cierto servicio no es necesario, antes debe demostrar que el instrumento puede detectar una dependencia conocida dentro del mismo entorno.

Si la instrumentación es incapaz de observar un positivo conocido, no puede transformar la ausencia de observaciones en una prueba negativa.

Este principio aparece explícitamente en el estándar Context-First adjunto.

### 9.4. Novel-Product Examinations

El examen más exigente sería presentar a USCI una clase de producto novedosa, con una descripción breve y sin su checklist completo.

El sistema tendría que derivar obligaciones mediante composición de mecanismos, conocimiento transferible y razonamiento sobre resultados.

La evaluación utilizaría un conjunto de responsabilidades previamente definido por revisores independientes, más revisión posterior de candidatos nuevos que pudieran ser legítimos.

Eso es necesario para no confundir «el agente descubrió algo diferente al answer key» con «el agente cometió un error».

### 9.5. Historical Future Holdouts

También aprovecharía repositorios con historias de evolución ricas.

Se congela el conocimiento del sistema en una versión antigua.

Se ocultan cambios posteriores.

Y se evalúa qué problemas, obligaciones o investigaciones habría anticipado USCI.

Los commits futuros sirven como evidencia de problemas reales, pero no como definición automática de arquitectura óptima.

Esto permitiría probar capacidad predictiva en lugar de memoria retrospectiva.

### X. Scope Capital Allocation: decidir qué merece entrar y qué debe eliminarse

Una inteligencia de scope verdaderamente madura no debería producir únicamente software más completo.

Debería producir software cuya complejidad esté mejor justificada.

Para ello utilizaría IFC como propietario de las decisiones de inversión, alimentándolo con datos generados por USCI.

### 10.1. Coste real del scope

Una capacidad puede parecer pequeña en términos de código, pero incorporar obligaciones importantes.

Por ejemplo, añadir un sistema de notificaciones persistentes puede afectar almacenamiento, preferencias, reintentos, entregas duplicadas, privacidad, operaciones, compatibilidad y observabilidad.

El compiler debe estimar el scope inducido.

No basta con calcular cuántas líneas requiere implementar la funcionalidad.

### 10.2. Scope Complexity Ledger

| Dimensión          | Qué contabiliza                                         |
| ------------------ | ------------------------------------------------------- |
| Build cost         | Trabajo inicial                                         |
| State cost         | Nuevos estados y transiciones                           |
| Interaction cost   | Nuevos acoplamientos                                    |
| Verification cost  | Nuevas pruebas y combinaciones                          |
| Operational cost   | Mantenimiento, monitorización y soporte                 |
| Recovery cost      | Recuperación y rollback                                 |
| Migration cost     | Compatibilidad y evolución                              |
| Security cost      | Nuevas fronteras de confianza                           |
| Cognitive cost     | Complejidad para usuario y operador                     |
| Institutional cost | Reglas, excepciones y deuda que CPP tendrá que mantener |

Cada nueva capability debería justificar este impacto.

Pero tampoco debemos convertir la simplicidad en una excusa para eliminar obligaciones necesarias.

El optimizador debe proteger todos los invariantes obligatorios.

### 10.3. Scope Portfolio Intelligence

Las funcionalidades no siempre tienen valores independientes.

Una puede aumentar el valor de otra.

Dos pueden resolver el mismo problema y resultar redundantes.

Una puede crear un nuevo archetype que cambia radicalmente el lifecycle.

Por eso evaluaría conjuntos de capacidades y no solamente features aisladas.

La búsqueda podría producir distintas configuraciones de producto válidas, con sus tradeoffs y costes de operación.

Las preferencias estratégicas genuinas corresponderían al Founder.

Los detalles técnicos derivados corresponderían al agente.

### 10.4. Scope Saturation

En algún momento el producto deja de necesitar más superficie y comienza a necesitar mejores integraciones, UX, performance y estabilidad.

USCI debería poder concluir:

> La siguiente mejora valiosa no consiste en añadir otra capability, sino en elevar la madurez de las que ya constituyen el producto.

Este detector sería especialmente importante para evitar que CBR se convierta en una fuerza de expansión permanente.

Una baseline madura puede crecer en garantías y calidad mientras disminuye en componentes y complejidad.

Ése sería un tipo de progreso institucional que deberíamos medir explícitamente.

### XI. Universal Proof-Carrying Scope Contract

Éste sería el artefacto técnico central, y lo convertiría en un objeto consumible por los demás sistemas de CPP.

No sería una especificación escrita solamente en Markdown.

Sería un contrato semántico serializable, con una presentación legible para agentes y humanos.

### 11.1. Qué debe contener

| Sección                  | Contenido                                              |
| ------------------------ | ------------------------------------------------------ |
| Product identity         | Propósito, consumidores, promesas y anti-goals         |
| World model              | Actores, recursos, estados, modos, versiones           |
| Scope obligations        | Requisitos derivados y sus condiciones                 |
| Exclusions               | Funcionalidades omitidas, prohibidas y no aplicables   |
| Responsibility graph     | Propietarios y consumidores                            |
| External estate          | Infraestructura y dependencias necesarias              |
| Constitutive inheritance | Baselines CBR aplicados con generación y razones       |
| Counterfactuals          | Fallos y transiciones relevantes                       |
| Verification plan        | Oracles, pruebas y cobertura                           |
| Unknown register         | Incertidumbres, materialidad y planes de resolución    |
| Decisions                | Autoridad, alternativas y justificación                |
| Scope lineage            | Versión, diferencias e historial                       |
| Invalidation             | Cambios que obligan a recompilar                       |
| Closure certificate      | Estado de cada dimensión y alcance de la certificación |

### 11.2. Proof-Carrying no debe significar Proof-Faking

Una obligación puede estar respaldada por diferentes tipos de evidencia.

Una prueba formal válida bajo un modelo no es lo mismo que una prueba de integración.

Una prueba de integración no es lo mismo que una observación en producción.

Una inferencia razonada no es una observación.

El certificado debe indicar claramente qué afirma cada evidencia y cuáles son sus límites.

Deberíamos tratar epistemic honesty como una propiedad verificable del compiler.

### 11.3. Certificados relativos, no omniscientes

Un contrato podría afirmar:

«Las obligaciones críticas conocidas bajo este modelo, esta versión, estos modos operativos y esta cobertura han sido satisfechas».

No debería afirmar:

«Se ha demostrado que el producto es perfecto en cualquier situación posible».

Eso es especialmente importante para software arbitrario, donde no existe un procedimiento general capaz de demostrar automáticamente todas las propiedades semánticas deseadas.

### 11.4. Scope Contract como entrada para ejecución

GSD X debería consumir una versión congelada.

El agente implementador podría elegir la mejor arquitectura de acuerdo con la realidad del repositorio, respetando sus invariantes.

Al descubrir información nueva podría proponer una revisión del contrato.

Pero no podría eliminar silenciosamente una obligación para conseguir pasar los tests.

Esto cumple directamente el estándar Context-First: precisión en resultados, invariantes y evidencia; libertad controlada en implementación.

### XII. Integración residente en Claude Power Pack

No ejecutaría la misma profundidad de análisis en todas las operaciones.

USCI debería ofrecer diferentes modos de compilación, seleccionados por incertidumbre, consecuencia y alcance.

| Modo                         | Cuándo                                      | Trabajo principal                                  |
| ---------------------------- | ------------------------------------------- | -------------------------------------------------- |
| Birth Compilation            | Nuevo proyecto o sistema importante         | Identidad, archetypes, obligaciones y estate       |
| Mission Delta                | Cambio dentro de arquitectura conocida      | Recompilar únicamente lo afectado                  |
| Architectural Reconciliation | Cambios en ownership, estado o arquitectura | Revisar contratos y efectos secundarios            |
| Release Certification        | Antes de desplegar                          | Scope delta, obligaciones y evidencia              |
| Incident Reconstruction      | Tras fallo o sorpresa                       | Reconstruir la omisión y su causa                  |
| Baseline Propagation         | Nueva generación CBR                        | Detectar consumidores y oportunidades de migración |
| Retirement Compilation       | Retirar sistemas o funcionalidades          | Migración, teardown y reachability negativa        |

### 12.1. Incremental Scope Compilation

Para evitar consumir enormes cantidades de tokens, los contratos deberían versionarse e incluir dependencias de evidencia.

Si cambia un componente que no afecta al grafo relevante, no hay razón para recompilar todo.

Si cambia la autoridad sobre un estado compartido, sí debe invalidarse la región afectada.

Esto produciría un compiler incremental.

### 12.2. Progressive Intelligence Budget

Propondría tres niveles de análisis.

FAST: reglas deterministas, índices semánticos, validación de contratos existentes y delta de dependencias.

DEEP: reconstrucción causal, investigación arquitectónica, propuestas de scope y contraejemplos.

CRITICAL: revisión independiente, modelos formales cuando aporten valor, pruebas de fallo y autorización de cambios de alto impacto.

Una tarea extensa pero conocida puede permanecer en FAST o DEEP.

Una modificación de diez líneas que cambia un writer canónico podría necesitar CRITICAL.

El criterio correcto es la incertidumbre arquitectónica y la consecuencia, no el número de archivos.

### 12.3. Observabilidad del propio compiler

USCI también necesita contratos de liveness y eficacia.

El historial de CPP ya muestra que una protección puede existir, ejecutarse parcialmente y aun así no producir evidencia audible.

Por tanto, sus etapas deben reportar:

STARTED, COMPLETED, SKIPPED_WITH_REASON, BLOCKED, FAILED o UNPRODUCED.

Un paso de discovery que nunca se ejecutó no puede equivaler a «no hay obligaciones nuevas».

Una etapa de verificación que expiró no puede convertirse en un éxito vacío.

Y ningún hook del compiler debería poder bloquear indefinidamente una sesión por esperar datos que no van a llegar.

Esto requiere límites efectivos sobre la cadena completa de procesos, limpieza de descendientes, estado recuperable y señales externas de liveness.

### XIII. Un ejemplo completo: de una petición mínima a un scope profesional

Supongamos que el Founder dice:

> «Construye una herramienta que genere y envíe facturas recurrentes automáticamente».

Un agente tradicional podría pensar en formularios, una base de datos, generación de PDF, un scheduler y correo electrónico.

USCI debería ir bastante más lejos, pero sin inventar un ERP completo.

COMPILACIÓN HIPOTÉTICA

Product Identity

Emisión recurrente y entrega fiable de documentos de facturación.

Constitutive Scope

Programación temporal, identidad de factura, generación correcta del documento, integridad de datos, seguimiento del estado, gestión de errores y evidencia de entrega o intento.

Derived Scope

Prevención de duplicación, reanudación tras crash, zonas horarias, coherencia de fechas, reintentos seguros, gestión de credenciales y autorización de efectos externos.

Conditional Scope

Requisitos fiscales, conservación documental, tratamiento de datos personales, numeración y reglas de emisión según jurisdicción y modelo comercial confirmado.

Shared / External Scope

Proveedor de email, plataforma de identidad, almacenamiento, infraestructura de scheduling y otros servicios existentes que puedan reutilizarse.

Negative Scope

Ningún pago duplicado si posteriormente se conecta un procesador; ninguna entrega no autorizada; ningún acceso entre clientes; ningún estado terminal falso tras un fallo parcial.

Deliberately Excluded

Contabilidad completa, marketplace, CRM y pasarela de cobros, salvo que sean necesarios para una promesa confirmada del producto.

Unknown / Founder Decisions

Jurisdicción, naturaleza fiscal de los documentos, destinatarios, grado de automatización autorizado y semántica comercial de cancelaciones.

El Founder no tendría que recordar que los schedulers pueden duplicar trabajos o que un proveedor puede fallar después de recibir una operación.

Esas obligaciones se derivarían de conocimiento institucional.

Pero tampoco deberíamos permitir que el agente invente unilateralmente las reglas fiscales aplicables: esa decisión requiere contexto y verificación normativa.

### El efecto multiplicador de CBR

Si anteriormente un proyecto de videojuegos enseñó a CPP a aislar estado temporal y persistente, ese mecanismo podría apoyar la distinción entre borradores, documentos emitidos y registros permanentes.

Si otro proyecto enseñó a CPP a restaurar trabajos después de crashes, el motor de facturas heredaría los requisitos de reanudación aplicables.

Si un tercer proyecto descubrió que un proveedor externo puede ejecutar una operación aunque la respuesta se pierda, el compiler anticiparía ese fallo.

Y si el propio sistema de facturación descubre una nueva forma de duplicación por reintentos y concurrencia, esa familia causal volvería a CBR.

No estamos reutilizando código de videojuegos para facturación.

Estamos reutilizando madurez de ingeniería.

### XIV. Blindaje institucional: cómo impedir que USCI se convierta en burocracia autónoma

El sistema debe poder fallar de forma segura.

Y, especialmente, debe resistir su propia tendencia a añadir scope.

| Riesgo                   | Protección                                                         |
| ------------------------ | ------------------------------------------------------------------ |
| Scope inflation          | Cada inclusión necesita una razón constitutiva o valor justificado |
| False universality       | Aplicabilidad, contraejemplos y promoción independiente            |
| Historical contamination | El código existente es evidencia, no autoridad automática          |
| Knowledge poisoning      | Separación entre contenido externo y reglas confiables             |
| False closure            | Estados UNKNOWN, UNPRODUCED y certificados limitados               |
| Duplicate ownership      | Resolución obligatoria de propietarios canónicos                   |
| Infinite discovery       | Presupuestos y criterio de parada basado en materialidad           |
| Expensive reasoning      | Compilación incremental y selección de profundidad                 |
| Self-certification       | Evaluación y ratificación independientes                           |
| Knowledge leakage        | Políticas de confidencialidad y transferencia entre proyectos      |
| Stale baselines          | Versionado, expiración de evidencia y recompilación                |
| Hidden regressions       | Historical replay, benchmarks ciegos y canary rollout              |

Aquí tomaría también una idea alineada con el SSDF de NIST: las prácticas deben adaptarse al riesgo, a las necesidades de la misión, a los recursos y a la aplicabilidad, en lugar de convertirse en una lista idéntica para cualquier proyecto.

### 14.1. No todo aprendizaje debe ser globalmente compartible

La transferencia de mecanismos puede requerir anonimización o abstracción.

Un incidente con datos privados, credenciales, decisiones contractuales o información comercial sensible no debe ser copiado sin control a una biblioteca general.

USCI debería poder transferir el patrón causal preservando las restricciones de acceso sobre la evidencia original.

### 14.2. Los cambios a la constitución deben ser más difíciles que los cambios de software

Una regla local afecta a un proyecto.

Una regla universal puede afectar a cientos.

Por tanto, cuanto mayor sea el alcance de una promoción, mayor debe ser su carga de prueba.

La misma lógica aplica a revertir baselines incorrectos: debe existir un mecanismo gobernado de supersession y rollback institucional.

Añadiría además pruebas metamórficas.

Una reformulación equivalente de la intención no debería producir scopes radicalmente diferentes sin motivo.

Una referencia contaminada con features innecesarias no debería expandir automáticamente obligaciones.

Una dependencia que desaparece del filesystem, pero sigue siendo necesaria en runtime, no debería desaparecer del scope.

Una baseline actualizada no debería debilitar una obligación crítica sin registrar una decisión autorizada.

Y una mejora del propio compiler debería demostrar mejor rendimiento sobre casos independientes, no solamente sobre los ejemplos utilizados durante su construcción.

### XVII. El siguiente nivel: una teoría institucional de completitud del software

Aquí aparece la consecuencia más ambiciosa de todo el diseño.

Con suficiente evidencia, CBR podría mantener modelos evolutivos de qué significa que diferentes categorías de software estén completas.

No solamente familias como «SaaS» o «plugin».

También estructuras abstractas como:

Durable Stateful Execution.

Authorized External Mutation.

Multi-Actor Shared State.

Reconstructable Infrastructure.

Human-Observable Autonomous Work.

Cross-Version Data Evolution.

Context-Dependent Authority.

Recoverable Distributed Coordination.

Cada una tendría una teoría constitutiva, precondiciones, contraejemplos, contratos, oracles y quizá primitives certificadas.

Cuando aparece un producto nuevo, USCI compone las teorías pertinentes.

Cuando surge un incidente nuevo, CBR puede modificar una teoría.

Cuando dos teorías entran en contradicción, USCI debe detectar el conflicto.

Cuando una teoría deja de explicar observaciones reales, necesita refinamiento.

Cuando una explicación causal más simple sustituye varias reglas particulares, CPP puede reducir su carga institucional.

Esto llevaría el flywheel más allá de acumular prácticas.

CPP comenzaría a acumular modelos explicativos de por qué ciertas arquitecturas son necesarias y bajo qué condiciones dejan de serlo.

Y hay otra consecuencia todavía más valiosa.

Una teoría puede revelar que seguimos implementando repetidamente la misma responsabilidad.

Entonces CBR puede proponer convertirla en primitive, plataforma o servicio compartido.

Así ocurre una transición:

Conocer la obligación → anticiparla → verificarla → automatizarla → eliminar su coste recurrente de construcción.

Ésa es la verdadera capitalización de una responsabilidad.

### XVIII. Las nuevas leyes que establecería

No las convertiría automáticamente en reglas ejecutables sin el proceso de promoción de CBR, pero serían candidatos constitucionales prioritarios.

| Ley                             | Principio                                                              |
| ------------------------------- | ---------------------------------------------------------------------- |
| Constitutive Inheritance        | Una construcción nueva debe heredar la madurez aplicable ya demostrada |
| Causal Responsibility           | La responsabilidad se deriva de resultados y efectos, no de carpetas   |
| Conditional Universality        | Toda generalización conserva sus condiciones y excepciones             |
| Negative Scope Proof            | Excluir responsabilidades materiales exige justificación               |
| Compositional Necessity         | Las interacciones pueden introducir obligaciones nuevas                |
| Temporal Completeness           | El scope incluye modos futuros relevantes, no solo el estado normal    |
| Architectural Freedom           | El contrato no impone una implementación sin necesidad                 |
| Epistemic Integrity             | Falta de evidencia no equivale a ausencia                              |
| Scope Anti-Laundering           | Una dificultad de implementación no autoriza debilitar el producto     |
| Counterexample Ratcheting       | Un fallo transferible debe mejorar el futuro detector aplicable        |
| Institutional Non-Duplication   | Ninguna nueva capacidad duplica propietarios canónicos                 |
| Independent Self-Evolution      | El sistema no puede certificar sus propias reglas nuevas               |
| Complexity Accountability       | Todo scope adicional debe justificar sus costes                        |
| Behavioral Institutionalization | El aprendizaje se demuestra mediante mejores decisiones posteriores    |

La más importante, para mí, sería ésta:

> A software engineering institution has not mastered a class of systems merely because it can implement them. It has mastered them when it can infer their necessary responsibilities, reject unnecessary complexity, verify their contracts, recover from their failures, and transfer that understanding to unseen systems.
