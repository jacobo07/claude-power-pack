# The constraint that shapes this burndown

A sibling pane sealed it while this was queued (`9b5ab1c`, `T-DUAL-BRANCH-GATE-001`):
**G1 judges a FILE.** One failing assertion anywhere clears the whole suite. So a
single unfalsifiable gate inside an otherwise rigorous file is invisible to G1 —
demonstrated on `tools/test_duplicate_to_advantage.py`, which G1 scores clean while
it carried a gate whose option-D path was never observed.

Two consequences for this work, both uncomfortable:

1. **Clearing G1 is cheap.** One assertion per file moves 58 to 0 without making a
   single suite rigorous. That is `T-FAILURE-ASSERTION-NOT-ARTIFICIAL-001` written
   as a work plan.
2. **The count is a floor, not a measure.** Files already clearing G1 may hold the
   same defect per-gate. Burning 58 to 0 must not be reported as "the estate is
   falsifiable now".

The burndown is still worth doing — a suite with zero failure assertions is
strictly worse than one with some — but the success metric is the failure modes
actually covered, not the number reaching zero.

# Proposed execution

Sprint 1 is TIER-1, taken in table order, top three first because `rule_compiler`
dominates churn. Per suite: read the module, find a real failure mode in its code,
assert the observable failure. If a module cannot fail on any reasonable input,
that is the finding and it gets reported rather than papered over with an invented
assertion.

Baseline is regenerated once at the end of the sprint so the ratchet falls by
name. TIER-2, TIER-3 and UNMEASURED go to OWNER_QUEUE; the ratchet already forces
any suite touched by future work to clear G1 before it can merge.

Resolving the UNMEASURED bucket needs a subprocess-aware subject resolver, which
is a separate instrument and is not built here.

# Outcome

The plan above assumed the 58 were happy-path-only suites. They were not. The
first TIER-1 entry, `test_egcc_residue.py`, already carried 13 negative-direction
checks, so the first unit of work went to the instrument instead of the list.

| step | G1 | cause |
|---|---|---|
| commissioned | 58 | — |
| D-001 `7c4e417` | 56 | helper form `_check("V-X", not bad, ...)` unseen |
| D-002 `37569c0` | 14 | inverted guard `if wrong: _fail(...)` unseen |

Forty-four suites moved with no test code changed. Both corrections were verified
by READING the newly-cleared guards, not by trusting the delta — which caught the
first attempt at D-002 negating the SUCCESS branch of `if COND: _ok(...)`, a
rubber stamp that cleared `test_wave_stagger.py` on `if worst <= 5`. Polarity is
now pinned by `V-PGG-G1-GUARD-POLARITY`.

**The remaining 14 are not a clean list either.** `test_fd04_acceleration.py`
requires `verdict == A.STALLED` on a stale ledger and is still flagged, because
`A.STALLED` is a module attribute rather than a readable string. Third
false-positive shape; each needs a new vocabulary, which is the defect itself.

**What settled it.** `test_ias_c2_opportunity_cost.py` gained six assertions that
feed bad input and require the rejection, every one traced to a branch in
`opportunity_cost.py`, and G1 did not move — they are spelled `is None` and
`== 0`. G1 can be satisfied by spelling and cannot be satisfied by rigor. No
assertion was reworded to please it.

**Successor.** `tools/mutation_probe.py` breaks the module and requires the suite
to go red. On `opportunity_cost.py` it found two gaps reading had missed
(settlement against a non-existent ledger; the aggregate's PROJECTED bucket), and
the measured kill count rose 4 -> 6 of 8 sampled. It reported one false SURVIVED
on its own first run — length-preserving mutants reusing a stale `.pyc` — caught
by hand-checking a mutant, fixed, and pinned by `V-MUT-DETERMINISTIC`.
