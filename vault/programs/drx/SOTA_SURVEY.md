## 1. future-house/paper-qa (PaperQA2)
- Pin: main @ c692d0dfeac4a0296599f7fe21a253a58b7ac12a (2026-10-26). Licence: Apache-2.0 (GitHub API).
- Files/functions: src/paperqa/core.py (`llm_parse_json`, `_map_fxn_summary`, `map_fxn_summary`); src/paperqa/docs.py (`aget_evidence`, `retrieve_texts`, `aquery`); src/paperqa/types.py (`Text`, `Context`, `PQASession.used_contexts`, `populate_formatted_answers_and_bib_from_raw_answer`); src/paperqa/prompts.py (`summary_json_system_prompt`, `qa_prompt`).
- Mechanism: each retrieved chunk (`Text`, linked to its `doc`) goes to an LLM that returns JSON {summary, relevance_score 0-10}. `Context` stores the LLM summary in `context`, the score, and the original chunk in `text`. Contexts with score > 0 are kept. Each Context gets a key `pqac-<8-char hash of question + first 500 chars of summary>`. The QA prompt shows keys with summaries and tells the model to cite keys in parentheses at sentence end. Post-processing maps cited keys to readable names/bibliography and strips keys not in the context map (hallucinated keys).
- Verbatim-quote check: none found in core.py/docs.py. The stored `context` is a paraphrased summary and nothing tests it against `text.text`. Citation check is key-existence only; nothing checks that the cited chunk supports the sentence.
- Claim classes: key generation, score parsing, `c.score > 0` filter, hallucinated-key stripping, absence of a quote check in core.py/docs.py: VERIFIED-IN-CODE. `PQASession.used_contexts` uses substring `c.id in self.raw_answer`: VERIFIED-IN-CODE; the false-match risk is OUR-HYPOTHESIS. UNREAD: `get_citation_ids`, `strip_citations`, `encode_id` (utils.py), so the exact key grammar is unverified; whether an evidence score cutoff setting is used elsewhere is not established.

## 3. stanford-oval/storm
- Pin: main @ fb951af7744dab086e34962e9bc6fe878e145f83 (2025-09-30). Licence: MIT (GitHub API).
- Files/functions: knowledge_storm/storm_wiki/modules/article_generation.py (`StormArticleGenerationModule.generate_section`, `ConvToSection.forward`, dspy signature `WriteSection`); knowledge_storm/storm_wiki/modules/storm_dataclass.py (`StormInformationTable.retrieve_information`, `construct_url_to_info`, `StormArticle.update_section`, `_merge_new_info_to_references`, `reorder_reference_index`, `post_processing`).
- Mechanism: for each section, top-k (default 5) `Information` items are retrieved by SentenceTransformer cosine similarity over stored snippets. `ConvToSection` numbers sources `[1]..[k]` (each with its snippets, capped at 1500 words) in the prompt; `WriteSection` tells the LLM to use `[1], [2], ..., [n]` inline. - Snippet-supports-sentence check: none. The [n] is a pointer to a URL with a set of snippets, not to one span; no offsets stored.
- Claim classes: all VERIFIED-IN-CODE (via summarizer). Summarizer-reported possible bugs (off-by-one in `update_section` range; `url_to_info` not pruned) are unconfirmed observations, OUR-HYPOTHESIS until re-read. `prune_empty_nodes`, `ArticleTextProcessing.update_citation_index` bodies UNREAD.

## Implications for our ledger
- paper-qa (pitfall): its evidence unit is an LLM summary kept beside the chunk, and the only answer check is "cited key exists". Our ledger must store the exact quoted span of the snapshot, never a paraphrase, and run the substring check on it.
- paper-qa (idea to adopt): a short stable key per evidence item embedded in the answer, with unknown keys stripped or rejected at output time; ours should be content-addressed (snapshot hash plus span offsets), not a hash of a summary.
- gpt-researcher (pitfall): citations are only prompt instructions to copy URLs; no verification or offsets exist, so a claim can cite a URL that never contained it. A claim without a ledger entry that passes the deterministic check must not render as supported.
- storm (pitfall): `[n]` points to a URL with a deduplicated set of snippets, losing which snippet backs which sentence. Our binding must be claim to (snapshot hash, start, end, quote), one-to-one.
- storm (idea to adopt): the post-hoc remap and prune of `[n]` markers (drop out-of-range, renumber by first appearance) is a cheap deterministic render pass, applied after the quote check.
- crawl4ai and docling (dependency decision): neither gives offsets from extracted text back to source bytes (crawl4ai none; docling HTML only whole-item `(0, len(text))`, and only with browser rendering). Keep the stdlib converter and define offsets over our own normalized text snapshot (hash that text, store offsets into it); do not adopt crawl4ai (extra attribution clause) or docling for this. Revisit docling for PDFs only after reading its PDF-side `CharSpan` semantics.
