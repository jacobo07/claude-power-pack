# External State of the Art: automated MATCHING decompilation (Wii/GC, mwcc) — 2026-11-20

Scope: what outside work could make our deterministic loop (dtk split -> m2c -> transform -> mwcc x2 flag sets -> objdiff) certify more functions, especially >=256 B, without human direction.
Tags: MEASURED (source given) / UNVERIFIED (claim not checked against a primary number, or my inference).
Method: web search + page fetches, ~40 tool calls, 2026-11-20. Page summaries were produced by a fetch model; numbers quoted below were read from the fetched page text, but I did not re-run anything.

## 1. Matching-decomp automation tools

### 1.1 decomp-permuter (simonlindholm)
- URL: https://github.com/simonlindholm/decomp-permuter
- What: random source-mutation search (temp vars, type changes, statement reorder/same-line, etc.) + manual PERM_* macros; score = objdump diff penalty, 0 = match; stack offsets ignored unless `--stack-diffs`. Supports MIPS (IDO/GCC), PowerPC, ARM32; repo ships an mwcc example script. Per-compiler mutation weights in `default_weights.toml`, overridable via `settings.toml`. `-j N` parallel; `-J` permuter@home (Docker, not native Windows). Ninja projects: `permuter_settings.toml` with `build_system = "ninja"`. (MEASURED: repo README, fetched 2026-11-20)
- Yield: README makes NO quantitative claim. FAQ: works best LATE, "when mostly register allocation differences remain"; random mode often yields nonsensical-but-matching changes. (MEASURED: README)
- Plug-in: near-miss class (>=90% objdiff, regalloc/ordering only). Our loop has the score already; the permuter only needs a compilable .c + target .s per function. Fixes: near miss >=90%. Does not fix far misses or compile fails.
- Published yields in agentic loops (both MEASURED, both NOT PPC):
  - Mizuchi benchmark (macabeus; agbcc GBA SA3 + IDO N64 Animal Forest, 60 fns, Sonnet 4.6, 12 attempts): programmatic stage (m2c+permuter) matched 0 SA3 fns, ~4 (m2c) + 3-4 (permuter) AF fns per run; permuter-in-background during AI phase helped 7 AF matches over 3 runs. Source: https://gambiconf.substack.com/p/can-llms-really-do-matching-decompilation
  - Snowboard Kids 2 (N64/IDO, Chris Lewis): permuter gated to >95% matches, then REMOVED: produced illogical code (`do{}while(0)`, nested assigns, variable reuse), sometimes deleted calls, and Claude treated its output as signal -> doom loops. Source: https://blog.chrislewis.au/the-long-tail-of-llm-assisted-decompilation/
- Lesson for us (UNVERIFIED inference): run the permuter as a DETERMINISTIC post-stage on our own near-miss pool (no LLM reading its output), accept only score==0, and keep the permuted source as-is (matching is the gate, readability is not). That avoids the documented doom-loop failure, which was specific to feeding permuter output back to an LLM.

### 1.2 Agentic matching-decomp loops (closest prior art to our loop)
- **Mizuchi** (macabeus) — https://github.com/macabeus/mizuchi ; write-up above. Plugin pipeline: m2c -> compile -> objdiff -> permuter, then Claude Agent SDK attempts; prompt carries up to 5 similar decompiled fns + caller/callee signatures + type defs. MEASURED: 74% avg match rate over 6 runs, best 80% (SA3 run 2); 53/60 identical outcome across runs; 12/60 always failed; ~half of post-programmatic matches came on AI attempt 1; if unmatched by attempt 3, ~1/4 chance of eventual match. Failure: agent's tool could not run objdiff so it falsely claimed matches; resubmitted identical code 49 times; "think deeper" stall prompt did little. NB: the 60 were curated easy/medium/hard tiers, not a random population, so 74% does NOT transfer to our 17-27% population number.
- **Snowboard Kids 2** (cdlewis) — https://blog.chrislewis.au/the-long-tail-of-llm-assisted-decompilation/ , https://blog.chrislewis.au/snowboard-kids-2-is-100-decompiled/ . MEASURED (author): match rate ~25% -> 58% fast with one-shot decompilation, -> ~75% then stall; finished 100% (project started Sep 2024). Mass m2c-only script over every unmatched fn: 17/1,830 matched (0.93%) (via HN summary https://prismix.dev/news/81141088c72f — secondary). Successful-attempt 85th percentile = 28 attempts; one fn needed 87; cap raised from 30 to uncapped. Queue: logistic-regression difficulty (instruction count, CFG complexity) -> stopped helping in the long tail -> replaced by "unmatched fns with a similar MATCHED counterpart first", similarity via coddog (bounded Levenshtein on opcode sequences) + hand n-gram/CFG/offset-stride score + asm text embeddings (the two scores disagreed on the top candidate in 90.6% of cases). Functions >1,000 instructions: "Claude usually gives up immediately". Math (matrix/vector) and macro-built display lists = persistent long tail. Opus main model; cheap GLM for cleanup.
- **decomp.wtf** (i12bp8, ARCHIVED, MIT) — https://github.com/i12bp8/decomp.wtf . Explicitly GC/Wii via dtk-template + objdiff in the project build. Design: per-function agent gets asm + touched data + callers + m2c draft + notes from earlier attempts; compile, link at real address, compare; only 100% counts; edits that break an already-matched fn are reverted; agent told to move on after 4 attempts without progress; no shell, no inline asm. Autopilot order: (1) functions IDENTICAL to already-matched code ("twins"), (2) machine drafts through the judge, (3) repeated code first, (4) files closest to completion first. Background permuter on >=95% near misses; coddog-style look-alike finder. MEASURED (README claim): Mario Party 6 — 762 functions matched in 12 minutes by autopilot twins (out of 17,923 without source); ~8 US cents per small function with Claude Code. No overall GC/Wii match rate published.
- Plug-in to ours: (a) TWIN propagation (byte/opcode-identical fns already matched in a donor or in the same game) is the single cheapest certified-per-minute number published for GC/Wii — fixes library code + duplicates; (b) similarity-first queue with matched-neighbour exemplars in the prompt — far miss / compile fails on the LLM tier; (c) attempt budget: success is long-tailed (p85 = 28 attempts in SK2) — our "2 certified / 1M tokens" may partly be budget spread too thin (UNVERIFIED); (d) objdiff MUST be callable inside the agent's loop (Mizuchi's top failure was its absence).

### 1.3 decomp-toolkit (dtk)
- URL: https://github.com/encounter/decomp-toolkit
- MEASURED (README): built-in signature DB "to identify common Metrowerks and SDK functions and objects" (used to auto-generate splits like `__init_cpp_exceptions`); high-accuracy function-boundary discovery; relocation rebuild -> "fully-shiftable objects"; auto-split of `.ctors/.dtors/extab/extabindex`; `dtk dol config main.dol rels/*.rel -o config.yml` (DOL + REL/RSO); `dtk dol diff config.yml build/main.elf` ("most obvious cause of a mismatch"); `dtk dol apply config.yml build/main.elf` (pull symbols from a linked ELF back into config); `dtk rso make`; `dtk disc verify` (Redump DB).
- NOT found: any documented public command to generate signatures from a donor project and apply them to a new binary. The sig DB is internal and small (older README listed "Add more signatures" as future work). UNVERIFIED whether the source has an undocumented sigs subcommand — worth a 10-minute look at `src/cmd/` before building our own.
- Plug-in: (a) `dtk dol apply` is the mechanism to pull donor-derived names/sizes back into config once a donor TU links; (b) the sig DB only NAMES library fns — naming is necessary for TU-level library transfer (section 6), it does not certify bytes.

### 1.4 coddog (ethteck)
- URL: https://github.com/ethteck/coddog
- MEASURED (README): `match <fn> -t 0.7` (similar fns in one binary), `cluster -m N` (near-identical groups), `submatch <fn> <n>` (shared n-length opcode runs), experimental `compare2 decomp.yaml us <other>/decomp.yaml us` and `compare-n` (cross-project). Similarity (per Lewis): bounded Levenshtein on opcode sequences, normalised 0-1. README does not state PPC support; its examples are N64 (UNVERIFIED for PPC — decomp.wtf says it "follows coddog's approach" for GC/Wii).
- Plug-in: cross-game twin finder between our target and the 6 donors at function level (opcode sequence, ignoring relocs/immediates). Fixes library code + duplicates; also supplies "similar matched neighbour" exemplars for near/far misses. If coddog lacks PPC, the algorithm is small over our existing dtk asm (UNVERIFIED effort estimate).

### 1.5 m2c
- URL: https://github.com/matt-kempster/m2c
- MEASURED (README): targets `ppc` + `mwcc` + `c`/`c++` (`-t ppc-mwcc-c` / `ppc-mwcc-c++`); `--valid-syntax`; `--context <file>` (repeatable, cached); `--stack-structs` (emit inferred stack struct `_m2c_stack_<fn>`, editable, fed back as context); struct field inference ON by default (`--no-unk-inference` disables); `--globals {used,none,all}`; `--void`; `--no-andor`; `--no-switches`; `--gotos-only`; `--deterministic-vars`; `--visualize`; partial C++ + CodeWarrior demangling; "compiler-specific heuristics for mwcc" (undocumented).
- Plug-in: the biggest m2c lever is `--context` with REAL headers (donor/SDK headers + our prelude) — struct inference and call signatures depend on it; plus fallback re-lifts with `--no-andor` / `--no-switches` / `--gotos-only` when the default lift fails to compile. Fixes: lift fails + compile fails. Effect size on mwcc NOT published (UNVERIFIED).

### 1.6 decomp.me
- URL: https://github.com/decompme/decomp.me (MIT, Django + Next.js, ships `docker-compose.yaml` -> self-hostable; compilers in containers via `cromper/`). (MEASURED: repo landing page)
- A scratch = target asm + source + context + compiler/flags (MEASURED: decomp.me FAQ). Third-party MCP `itsgrimetime/decomp-me-mcp` (https://claudemarket.ai/mcp/itsgrimetime/decomp-me-mcp) claims scratch load with full context and search filtered by platform `gc_wii` (UNVERIFIED, unofficial).
- Plug-in: (a) as a CORPUS — public matched gc_wii scratches are (asm, matching source, flags) triples: few-shot exemplars and twin sources. Bulk-scrape terms/consent = Owner question. (b) Self-hosting adds nothing our local compile+objdiff loop lacks. gc_wii scratch counts: NOT found.

### 1.7 mwcc internals tooling
- **rayanht/mwcc** — a matching decompilation OF THE COMPILER (frontend/optimizer/backend), with GC 1.0/1.1/1.1p units (https://github.com/rayanht/mwcc/commit/92f893fbcbb23d9833be5fc24ac9e069090f8729). doldecomp/sms AGENTS.md tells agents to read its `src/frontend`, `src/optimizer`, `src/backend` "when a codegen question is not answered by guessing". MEASURED existence; Wii/1.x coverage UNVERIFIED.
- **mwcc-debugger** (cadmic) — https://github.com/cadmic/mwcc-debugger . Runs mwcc under retrowin32 + gdb; dumps AST (initial/optimized/final), PCode between backend passes, regalloc priority-ordered variable list (GPR/FPR, incl. coalesced), stack layout (GC/1.1). Supports GC/1.1 (~GC/1.0-1.2.5) and GC/2.6 (~GC/1.3.2-2.7). Allocator as documented (MEASURED, README): simplify-style priority levels (var with fewer neighbours than free regs, usually 29, removed first; else lowest adjusted spill cost); colour highest priority first with the lowest-numbered free reg, preferring r0, r3-r12 and already-used saved regs, new saved regs from r31 downward; spill -> rerun; `mr` coalescing before allocation, with a known bug that leaves coalesced vars as neighbours (they still bias priorities). Levers: value as compiler temp vs named local, move code into an inline, add/remove interference via coalesced vars.
- Plug-in: turns a regalloc near miss from random search into a DIAGNOSABLE problem: dump our allocation order, compare to target register usage, find first divergence, apply a lever from a fixed menu. Fixes near miss >=90%. Wii/1.x compilers are NOT in its supported list (UNVERIFIED whether the GC/2.6 profile transfers). Maturity: research tool; needs gdb + a Rust build.

## 2. mwcc codegen quirks and source patterns that force a match

Primary source: doldecomp/sms AGENTS.md (https://raw.githubusercontent.com/doldecomp/sms/HEAD/AGENTS.md), written FOR LLM agents on an mwcc GC project (MEASURED: content of that file). Key rules:
- Flags (SMS game code): `-O4,p -fp_contract on -str reuse,readonly -opt all,nostrength -inline deferred`; GC/1.2.5 for most, GC/1.2.5n for some SDK files. C++98 Metrowerks dialect; RTTI/exceptions off. => flags are PER-TU and per-library; our "2 flag sets" is likely under-sampled for SDK/MSL TUs (UNVERIFIED for our games — check donor `configure.py` per-library cflags).
- `-inline deferred` REVERSES emission order of functions in a TU vs source order (most game TUs); some libraries (JAudio) follow forward order. Matters only when compiling whole TUs (not single-function objects) — but it changes which inlines happen.
- Inlining: mwcc inlines small header/`inline` fns aggressively; `#pragma dont_inline on/off` forces a standalone copy but "always hides a real cause". Structural mismatches are usually an inlined early-return callee -> recover with a TU-local `static inline` helper. A plain `static` helper stays emitted (shows as UNUSED); fabricated helpers must be `inline`/`static inline`.
- Loads/stores: "Any function call in MWCC invalidates all cached loads, most stores to memory do too" — use reloads in the target asm to locate call boundaries/aliasing in the original.
- Fix order: control flow and call order -> load/store order -> operand-level. In objdiff, `|` opcode differs, `<` / `>` deleted/inserted = real problems; `~` (reg renumber / stack offset) often resolves after structural fixes.
- Stack-frame-only diffs: many spellings close a frame deficit (pads, extra locals) — `volatile char trash[N]` allowed only to validate; "If only stack offsets still differ, stop" (for a project that rejects fakematches; for our certification purpose a pad that matches IS byte-identical — Owner policy decision, flagged).
- Do not copy globals/members into locals only to move codegen (project-style rule; it is also a regalloc lever).
- `const` on globals changes the emitted section; include order affects BSS layout and static-init order.
- Accessor-consistency test: a hypothesised inline accessor must be tested at every site; if any site gets worse it is refuted.
- Regression discipline: `ninja baseline` before, `ninja changes_all` after; read the full report (improved/worsened/reached/lost 100%).
- Agents are prohibited (without humans) on MSL runtime, MetroTRK, THPPlayer, dolphin SDK, JSystem: library code is where human-only knowledge concentrates (and where transfer from donors, not generation, should be used).
Other community material:
- Register allocation detail: section 1.7 (mwcc-debugger). A community KB PR claims saved registers are handed out by descending vreg index (UNVERIFIED community finding): https://github.com/rehan-remade/universal-modder/pull/275 . Melee register skill: https://deepwiki.com/stephenjayakar/melee-mwcc-register-skill (not read).
- `#pragma ipa file`: static declaration order decides offsets (DS mwcc project, https://github.com/mikeybear99/fossil-fighters-decomp) — different mwcc target, UNVERIFIED for PPC.
- Plug-in to our loop: the "light transform" stage can carry a fixed, ordered MENU of mwcc levers to try deterministically on near misses before any permuter/LLM: (1) re-lift as C++ vs C, (2) inline/static-inline extraction of repeated blocks, (3) temp vs named local for each regalloc-divergent value, (4) per-TU flag sets from the donor library's configure.py, (5) declaration order of locals. Fixes near miss >=90% and some far misses (structural). Effect size: NO published numbers (UNVERIFIED).

## 3. ML / LLM research on (matching) decompilation

Academic work optimises FUNCTIONAL correctness (re-executability) on x86 GCC, not byte-exact matching on mwcc — transfer to our task is weak.
- **LLM4Decompile** — https://github.com/albertan017/LLM4Decompile . MEASURED (README): re-executability End-1.3B 27.3%, End-6.7B 45.4%, Ref-9B-v2 64.9%, Ref-22B-v2 63.6%; Linux x86_64 GCC O0-O3 only; no byte-exact metric. Datasets: decompile-bench ~2M binary-source pairs. Not applicable to PPC/mwcc without retraining.
- **SK2Decompile** (ICLR 2026) — https://arxiv.org/abs/2509.22114 . Two phase (skeleton -> skin/identifiers), compiler-checked RL reward; notes recompilation needs exact function/type/field names (MEASURED: abstract/summary). Functional, not matching.
- **AutoDecompiler** — https://arxiv.org/abs/2606.16162 . RL-trained multi-turn refinement; rewards = validity, recompilability, execution consistency, semantic fidelity; stage-aware diagnostics from compiler errors/test failures (MEASURED: abstract). Functional.
- **RlDecompiler** — https://dl.acm.org/doi/pdf/10.1145/3794763.3794807 . RL with multi-part reward (syntax, similarity, compilability, structure, params, signature, AST). Functional.
- **Decaf** — https://arxiv.org/abs/2605.11501 . Compiler feedback + sampling + neural reranker (no RL training). Functional.
- **Echo** — https://arxiv.org/abs/2609.18706 . The one paper that targets MATCHING decompilation: generates candidate source AND compilation configuration, recompiles, scores asm-level similarity, repairs via rule-based rewriting -> neural refinement -> reasoning refinement. MEASURED (abstract): 2.43x more exact matches than the strongest baseline on average; on Mirai 2.75x GPT-5.6 and 7.4x Codex. Absolute rates, arch/compiler, code release: NOT stated in abstract (read the PDF before relying on it). Architecture is essentially our loop + a rule-rewrite stage + config search — the "search the compile configuration too" part is the transferable idea.
- **Hugging Face N64 fine-tune blog** (Reingold) — https://huggingface.co/blog/MatthewReingold/n64-decomp-dev-blog . MEASURED: trained on ~23,400 "perfect" decomp.me scratches obtained as a PostgreSQL dump from decomp.me (95/5 split, ~1,171 eval); 93% of data on ido7.1/ido5.3/gcc2.7.2kmc/gcc2.8.1pm (almost no mwcc); LoRA r16. Byte-exact: stock LLM4Decompile-6.7B 5/1,171; 9B-v2 on Ghidra input 10 (compiled 53); Nemotron-32B fine-tune 14 (compiled 58). Score distribution bimodal (0 or >=500). RL with compiler reward proposed, not done. => small fine-tuned models are FAR below frontier agent loops; the useful asset is the decomp.me DUMP (exists and was shared on request), not the model.
- **Practitioner agent loops** (section 1.2) are the only measured evidence of byte-exact automation at scale: Snowboard Kids (N64, 2,145 fns, 84 days, ~4.8% of matching commits needed expert help; author estimates a stall at 89-90% without experts — https://blog.chrislewis.au/decompiling-a-nintendo-64-game-in-84-days/), SK2 (2,995 fns, 596 days), Melee (GC/mwcc, below). Feedback signal everywhere = compile errors + objdiff/asm-differ diff + percentage; nobody published objdiff-as-RL-reward training for mwcc.
- New idea from SK1 (MEASURED existence, no effect size): "N64 Decomp Workbench" classifies mismatches and REPLAYS COMPILER PASSES to separate structural problems from register-allocation problems; agents get per-task deadlines (time-boxed permuter); a shared DECOMPILATION_LEARNINGS.md of compiler quirks; similarity search across all worktrees so a fresh match is an exemplar immediately.

## 4. Strategies for large functions (>=256 B)

Evidence that large functions are THE wall for everyone: SK2 ">1,000 instructions: Claude usually gives up immediately" (MEASURED, Lewis); HF blog matches "mostly small or empty functions" (MEASURED); our own 0-7%. No source published a large-function technique with an effect size. What exists:
- **Inline extraction**: mwcc inlines aggressively; structural mismatches are "usually inlined early-return callees" -> recover with TU-local `static inline` helpers (SMS AGENTS.md, MEASURED as guidance). For a large function, the body is often N inlined helpers, and the donor projects may already have those helpers as header inlines (e.g. NW4R/EGG/JSystem math/list accessors). Plug-in: lift with donor headers in `--context` so m2c emits calls to existing inlines' callees and the LLM sees the library's inline vocabulary (UNVERIFIED effect).
- **Fix order** (structure -> load/store -> operands) and "a function call invalidates cached loads" let you locate inline boundaries and call sites mechanically (SMS AGENTS.md).
- **Mismatch classification** (structural vs regalloc) before spending: SK1 Workbench; mwcc-debugger gives the same split for mwcc GC versions. Spending permuter/LLM attempts on a regalloc-only large function is a different job from a structural one.
- **Partial-credit stepping stones**: objdiff gives a per-function % — a large function can be driven in chunks (first make CFG/call order identical, then lower diff count). decomp.wtf/Mizuchi both use the diff as the inner signal. For a deterministic loop, accept "improved diff count" as progress state, not only 100% (UNVERIFIED effect).
- **Type recovery**: struct layouts from donor headers (same engine families: NW4R, EGG in ss/mkw/ogws-family, JSystem in tp/petari), from dtk-inferred object sizes, from vtables in `.data` (dtk splits ctors/vtables; mwcc vtable layout gives class hierarchy), from `__FILE__` assert strings in `.rodata` (pacman-party recovered source filenames that way: https://github.com/Code-6dof/pacman-party-decomp) and from map files / debug builds (SMS uses `marioL.MAP`; Petari, TP have symbol maps). RTTI is off in many Nintendo builds (SMS) so do not count on it (MEASURED for SMS only).
- **Debug/other-region builds**: TP's Wii and Shield versions, SMS's 5 versions — multiple builds of one source multiply constraints (one source must match all). Only useful if our targets have kiosk/demo/debug builds (UNVERIFIED for our games).
- Honest read: the external world has NOT solved autonomous matching of large mwcc functions; Melee finished its tail with frontier agents + human direction (section 5). Expect large functions to be the last 20-30% regardless.

## 6. Library / SDK sharing

- **Evidence that wholesale transfer works (MEASURED):** pbr-decomp PR #38 (https://github.com/pbr-ret/pbr-decomp/pull/38, merged 2026-11-02) imported 15 NW4R `ut` TUs from doldecomp/ogws (CC0) unchanged in logic; each 100% code+data, DOL SHA-1 identical; decomp.dev bot: +143 matches. Edits needed were integration-only: include-path/case, project DVD names, missing extern decls (`floorf`, `PSMTX*`, `OSInitFont`...), one arg order (`GXSetFog`), dropping ogws shims, removing `FORCEACTIVE`, choosing the right ogws revision macro (`VERSION_RSPE01_00/_01`). Built with "SDK flags + `-DREVOLUTION`". This is the cheapest bytes-per-effort move in the whole field.
- **Sources of matched library code by version:** doldecomp/ogws (Wii Sports: RVL SDK + NW4R; RVL SDK category 69.04% on decomp.dev: https://decomp.dev/doldecomp/ogws/RSPE01_01?category=sdk&mode=history), kiwi515/open_rvl (archived 2024-02-20; targets Wii Sports SDK `__MWCC__ == 0x4199_60831`, "adaptable to other projects with minimal effort": https://github.com/kiwi515/open_rvl), plus our donors petari/ss/tp/xenoblade/mkw (each carries its own SDK/NW4R/MSL/Runtime at its own version). Petari wiki: SMG1 game GC 3.0a3; RVL_SDK, NW4R, JSystem, MSL GC 3.0; MetroTRK GC 2.5 (https://github.com/SMGCommunity/Petari/wiki/CodeWarrior) — i.e., libraries use DIFFERENT compiler versions from game code.
- **Identifying the SDK version of a binary (MEASURED practices):** (1) the per-library banner strings in `.data`/`.rodata`: `<< RVL_SDK - EXI release build: <date> (0x4199_60831) >>` style lines (Wii Sports: https://redoste.xyz/2020/04/21/modding-wii-sports-part-i-identifying-files-and-creating-a-debug-output/); the hex tag is the mwcc build, the date the SDK build; (2) RevoEX/SDK version strings (monsterlab: "RVL_SDK RevoEX 2.1plus, build 080313085908": https://github.com/BrammekeTV/monsterlab-decomp; pacman-party: `0x4302_145`, Dec 11 2009); (3) "initialization functions for some libraries print out the compiler build" (Petari wiki); (4) empirical: link a donor TU and check the SHA/objdiff (pbr PR #38). No authoritative public table version->tag exists (searched; NOT found).
- Plug-in to ours: per target game, grep the banner strings -> pick the donor whose banner date/tag is closest per library (OS, GX, DVD, NAND, WPAD, NW4R ut/lyt/snd/g3d, MSL, Runtime) -> import whole TUs with the donor's per-library cflags -> objdiff per function -> keep matching functions, fall back per function for the rest. Addresses library code (12-91% of bytes per game). Requires TU-boundary agreement with dtk splits (dtk sigs + `dtk dol apply`).
- Ghidra FID / FLIRT-style DBs for GC/Wii SDK: none found (searched). Ghidra needs the community GameCube loader / gekko-broadway language for paired singles (https://wiibrew.org/wiki/Ghidra). ## 7. Ranked interventions for OUR loop (expected certified functions/bytes per unit effort)

Effort = engineering days to wire into the deterministic loop. Confidence is mine; every number cited is from the sections above.

1. **Whole-TU library transplant from donors, version-matched by banner strings** — library code. Grep `RVL_SDK - <lib> release build: <date> (<tag>)` lines in each target; pick the donor with the same/closest tag per library; import donor TUs with the donor's per-library cflags; objdiff per function; keep the 100% ones. Evidence: pbr PR #38, 15 ogws `ut` TUs -> +143 matches, SHA-identical, integration-only edits (MEASURED). Library = 12-91% of our bytes, and it includes many large functions our generator can never match. Effort: medium (header reconciliation per donor). Confidence: HIGH that it certifies thousands of functions across 6 games; MEDIUM on how many survive version drift.
2. **Cross-game twin propagation (opcode-sequence, reloc-masked)** — library code + duplicates + large functions. Hash/align every target function against every MATCHED function in the 6 donors (and against our own certified set) a la coddog / decomp.wtf "twins"; compile the donor's source for exact twins; send near-twins (>=0.9 similarity) to the near-miss stage with the donor source as the starting point. Evidence: decomp.wtf autopilot twins, Mario Party 6: 762 fns in 12 min (MEASURED, README claim). Effort: low-medium. Confidence: HIGH. Size-independent, so it is the only listed lever that reaches >=256 B functions cheaply.
3. **Per-TU compiler version x flag sweep instead of 2 global flag sets** — compile fails / near miss / far miss. Libraries use different mwcc versions from game code (Petari: game GC 3.0a3, SDK/NW4R/MSL GC 3.0, MetroTRK GC 2.5 — MEASURED); SMS game flags `-O4,p -fp_contract on -str reuse,readonly -opt all,nostrength -inline deferred` vs separate SDK settings (MEASURED); Echo searches compile configuration as part of matching (MEASURED, 2.43x exact matches vs baseline, setup unspecified). Take each donor's `configure.py` per-library cflags as the candidate grid. Effort: low. Confidence: MEDIUM-HIGH that a meaningful share of our "compiles but <100%" pool is a wrong-flags/version artefact (UNVERIFIED for our data — measure by re-scoring certified-elsewhere library fns).
4. **Compile whole TUs (not one function per object) once a TU is mostly lifted** — near miss / far miss. `-inline deferred` reversal, `static inline` helpers, header inlines, `.sdata`/string pooling (`-str reuse`) and section placement are TU-level effects (SMS AGENTS.md, MEASURED as guidance). Effort: medium. Confidence: MEDIUM.
5. **Deterministic decomp-permuter post-stage on the >=90% pool, accept only score 0, never shown to an LLM** — near miss >=90%. Evidence: Animal Forest permuter 3-4 matches/run on 30 fns + 7 assisted (IDO; MEASURED); README: best when "mostly register allocation differences remain"; SK2 removed it only because the LLM fed on its output (MEASURED). Settings: `-j <cores>`, mwcc weights via `settings.toml`, time-box per function (SK1 deadlines). Effort: low (already installed). Confidence: MEDIUM — yield on mwcc PPC unpublished; mwcc example exists in repo.
6. **m2c with real context** (donor/SDK headers through `--context`, `--stack-structs` round-trip, fallback re-lifts `--no-andor`/`--no-switches`/`--gotos-only`, C++ target for C++ TUs) — lift fails / compile fails. Effort: low-medium. Confidence: MEDIUM for compile rate; LOW for direct matches (SK m2c-only batch matched 0.93% — MEASURED; ours already 17-27%).
7. **LLM tier rebuilt on the published pattern: similarity-first queue, 3-5 matched neighbour exemplars, objdiff callable in-loop, fewer functions with larger budgets** — far miss / near miss. Evidence: SK2 25% -> 75% with this pattern (MEASURED, N64 IDO); Mizuchi: ~half of matches on attempt 1, ~1/4 chance after attempt 3 (MEASURED); SK2 successful p85 = 28 attempts (MEASURED). Effort: medium. Confidence: MEDIUM that it beats our 2 certified/1M tokens; IDO -> mwcc transfer UNVERIFIED.
8. **Mismatch classifier (structural vs regalloc vs frame-only) routing** — near miss / far miss. objdiff diff kinds + (for GC-version TUs) mwcc-debugger allocation dumps; regalloc-only -> permuter/lever menu; structural -> LLM/inline extraction; frame-only -> pad policy decided by the Owner (byte-identical pads certify bytes; SMS rejects them as fakematches). Evidence: SK1 Workbench exists (MEASURED, no effect size); mwcc-debugger supports GC/1.0-2.7 only (MEASURED). Effort: medium. Confidence: MEDIUM-LOW.
9. **Exemplar corpus from decomp.me + all donor repos** — far miss. decomp.me supplied a ~23,400-perfect-scratch PostgreSQL dump to one researcher (MEASURED); mwcc share of it unknown (the cited subset was 93% IDO/GCC). Use as retrieval exemplars, not fine-tuning (fine-tuned 9-32B models: 10-14 byte-exact of 1,171, MEASURED). Effort: low (ask) to medium. Confidence: LOW-MEDIUM.
10. **Large-function chunking** — large functions. Accept monotone objdiff improvement as saved state; extract inlined helpers using the donor's header inline vocabulary; fix structure -> loads/stores -> operands in that order. Evidence: no published effect size anywhere; SK2 agents give up >1,000 instructions (MEASURED). Effort: high. Confidence: LOW — after items 1-2 take the library share, the remaining large game-code functions are where everyone, Melee included, used human-directed frontier agents.

Not recommended (evidence against): fine-tuning a small model (item 9 numbers); letting an LLM read permuter output (SK2); a "think deeper" stall prompt (Mizuchi); m2c-only batch as a match source (0.93%).
