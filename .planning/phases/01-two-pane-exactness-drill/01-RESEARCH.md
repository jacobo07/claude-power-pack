## Question 1 — The delivery contract (`extension/src/terminal_inbox.js`)

`decide(req, terminals, session, nowMs)` returns `send` only if ALL of the following hold, in this order [VERIFIED: extension/src/terminal_inbox.js:68-86, read this session]:

1. **`req` is a non-null object** — else `{action:"ignore", reason:"no-request"}` (`terminal_inbox.js:69`).
2. **Ownership — exactly one match.** `ownedTerminals(terminals, req.ancestors)` intersects this window's terminal `processId`s against `req.ancestors` (an array of pids). `req.ancestors` must contain a pid that equals a `processId` of one of `terminals` (`terminal_inbox.js:54-61`).
   - Zero matches → `{action:"ignore", reason:"not-this-window"}` (`:71`) — **silent from this window's perspective** (see extension.js below for whether ignore writes anything).
   - More than one match → `{action:"refuse", reason:"ambiguous-terminal"}` (`:72`).
3. **Not expired.** `ttl = req.ttl_ms` (finite) else `DEFAULT_TTL_MS = 60000` (`:27,74`). Must satisfy `nowMs - req.created_ms <= ttl` AND `req.created_ms` must be finite. Violated → `{action:"refuse", reason:"expired"}` (`:75-77`).
4. **Valid text.** `req.text` must be a string, length 1–512 inclusive, with no control characters (charCode < 32 or ===127, checked per-codepoint via spread) (`validText`, `:47-51`). Violated → `{action:"refuse", reason:"invalid-text"}` (`:78`).
5. **Session readable.** `session` must be a non-null object, else `{action:"refuse", reason:"session-unreadable"}` (`:80`).
6. **Session id match.** `session.sessionId === req.session_id` (strict equality), else `{action:"refuse", reason:"session-mismatch"}` (`:81`).
7. **PID match.** `session.pid === req.claude_pid` (strict equality), else `{action:"refuse", reason:"pid-mismatch"}` (`:82`).
8. **procStart match within tolerance.** `sameProcStart(session.procStart, req.proc_start)` — both values parsed as unsigned decimal BigInt strings (regex `^\d+$`); non-numeric or unparsable → treated as unequal (`toBig` returns `null` → `sameProcStart` returns `false`). Absolute difference must be `< 10n` (FILETIME 100ns units, i.e. <1 microsecond) (`:28,39-45`). Violated → `{action:"refuse", reason:"proc-start-mismatch"}` (`:83`).
9. **Status exactly `"idle"`.** Any other value (e.g. `"waiting"`, `"busy"`) → `{action:"defer", reason:"status-<value>"}` (`:85`) — NOT refuse, NOT send.
10. Only if all the above pass → `{action:"send", terminalIndex: owned[0]}` (`:86`).

**Fields a request (`req`) must carry**, per the self-test fixture (`:106-110`, [VERIFIED: same file — this is the literal test fixture, not paraphrase]):
```
{ id, session_id, text, claude_pid, proc_start, ancestors: [...pids], created_ms, ttl_ms }
```
Every field above is read by `decide()` except `id` (not referenced inside `decide`, presumably used by the caller/extension.js for ack bookkeeping — see Q1 continued below).

**Four possible outcomes, not three:** `ignore`, `defer`, `refuse`, `send` — the phase context's list ("send/ignore/refuse/defer") matches exactly these four action strings.

### Q1 continued — ack-file / silence behavior (`extension/src/extension.js:57-119`, read this session)

Request file naming: `~/.claude/state/terminal-inbox/<sid>.req.json` [VERIFIED: extension.js:36 `INBOX_DIR = ...terminal-inbox`; extension.js:34 comment states the pattern explicitly: request is `<sid>.req.json`, acknowledgement is `<sid>.ack.json`]. Ack file: `~/.claude/state/terminal-inbox/<session_id>.ack.json` (`extension.js:50-51`, keyed by `req.session_id` at write time — NOT necessarily the same string as the request filename's sid, though in practice they should match).

Per-action ack behavior:
- **`ignore`** (`extension.js:81`, `continue`) — **fully silent**. No ack written, request file untouched (not renamed/claimed), no ledger entry at all. Every OTHER window with a live extension also sees the same `.req.json` and independently ignores it until the true owner claims it.
- **`defer`** (`extension.js:82-93`) — writes an ack **once per request id** (`inboxDeferNoted` Set dedupes) with `status: "deferred"`, `reason: d.reason` (e.g. `status-waiting`, `status-busy`). The `.req.json` file is **NOT renamed/claimed** — it stays in the inbox dir for retry. `inboxTimer` re-polls every `INBOX_RETRY_MS = 500` ms (`:38,117`) until it stops deferring.
- **`refuse`** (`extension.js:100-101`) — request is claimed first (renamed to `<name>.<pid>.claimed`, `:96-97`), then ack written with `status: "refused"`, `reason: d.reason`, then the claimed file is deleted (`:109`). **This IS the mechanism the phase's Done criterion needs**: "one deliberately unowned request is ledgered `refused` with its reason" — reason values come directly from `decide()`'s reason strings (`ambiguous-terminal`, `expired`, `invalid-text`, `session-unreadable`, `session-mismatch`, `pid-mismatch`, `proc-start-mismatch`).
- **`send`** (`extension.js:102-108`) — request claimed, `term.sendText(req.text, false)` then a 250ms delay (`ENTER_DELAY_MS`, `:39`) then `term.sendText("\r", false)` (separate keystroke so a TUI doesn't read text+Enter as one paste), then ack `status: "sent"`, `terminal: term.name`, then claimed file deleted.

**Important nuance for the drill:** "ignore" is complete silence from that window — it does not write anything, not even a negative record. Only the **owning** window (the one whose terminal pid is in `req.ancestors`) ever writes an ack for a given request, after `defer` (repeatable)/`refuse` (terminal)/`send` (terminal). So B's pane, if genuinely not the owner of A's request, produces **zero artifacts** in `terminal-inbox/` for that request — absence of any ack from B is the expected (unrecorded) state, not a written negative record.

**Also note:** `readJson` at `extension.js:46-48` strips a leading UTF-8 BOM (U+FEFF) from the file text before `JSON.parse` — consistent with the global CLAUDE.md "BOM defeats JSON.parse" lesson; this file already guards against it. The drill's own request-writing step (for the "deliberately unowned" case) should still write plain UTF-8 **without** a BOM, to keep behavior deterministic and not rely on this survival path.

**Where session transcripts live:** `find_transcript(session_id)` (`:213-220`) globs `<projects_dir()>/*/<session_id>.jsonl` and returns the first match. `projects_dir()` (`:134-136`) returns `$env:GSD_LONG_RUN_PROJECTS_DIR` if set, else the module constant `PROJECTS_DIR = CLAUDE_HOME / "projects"` (`:37`) — i.e. **`~/.claude/projects/<workspace-hash-dir>/<session_id>.jsonl`** (standard Claude Code transcript location; the exact value of `CLAUDE_HOME` was not re-read this session, but the constant name and downstream usage make this layout unambiguous). This matches the scratchpad path visible in this session's own environment block (`...\.claude\projects\C--Users-User--claude-skills-claude-power-pack\...`), corroborating the layout.

**The predicate that proves user submission, exactly** — `user_issued_command_since(transcript, command, since_epoch)` (`:290-308`):
```python
name = (command or "").split()[0] if command else ""
if not name:
    return False
for row in _tail_rows(transcript):
    if row.get("type") != "user":
        continue
    ts = _parse_iso(row.get("timestamp"))
    if ts is None or ts < since_epoch:
        continue
    text = _text_of(row.get("message"))
    if f"<command-name>{name}</command-name>" in text or text.strip().startswith(name):
        return True
return False
```
(verbatim from `:296-308`). In words, a row counts as proof only if **all** of:
1. `row["type"] == "user"` (`:300-301`) — the load-bearing distinction, per the docstring: "Claude Code records a slash command as `<command-name>/name</command-name>`; typed text is recorded verbatim. Either counts." (`:293-294`). A `type:"assistant"` row echoing the text, or a system/tool row, can never satisfy this regardless of content.
2. `row["timestamp"]` parses (`_parse_iso`, referenced at `:143`, not re-read line-by-line this session) to a time `>= since_epoch` (`:302-303`) — scopes the check to "since the drill's own submission attempt", so a stale pre-existing occurrence of the same command text earlier in the transcript cannot false-positive.
3. The row's flattened message text (`_text_of`, handles either a plain string or a list of `{type:"text", text:...}` content blocks, `:264-272`) contains either the exact substring `<command-name><first-word-of-command></command-name>` (the slash-command XML tag Claude Code's transcript format uses) **or** the trimmed text simply starts with that first word (covers typed/non-slash text).

Only the **first whitespace-delimited token** of `command` is checked (`name = command.split()[0]`) — for a resume line like `/gsd-autonomous --from 10.1`, the predicate checks for `<command-name>/gsd-autonomous</command-name>` or text starting with `/gsd-autonomous`; it does **not** verify that a trailing argument (`--from 10.1`) matched. Real gap for the planner to note: this proves *a* command of that name was submitted after the timestamp, not that the exact resumed-continuation text matched byte-for-byte. For this phase's Done criterion (pane A got the resume line, pane B got nothing) this is almost certainly sufficient, since pane B's check is for **absence of any matching `user` row at all**, not for a wrong argument on a present one.

**Reading transcripts as evidence, not the daemon log:** `_tail_rows` (`:242-261`) opens the transcript file in binary mode, seeks to `max(0, size - tail_bytes)`, decodes UTF-8 with `errors="replace"`, and drops the first (possibly truncated) line if the file was larger than the tail window. Both `user_issued_command_since` and `last_assistant_text`/`compaction_observed` build on this same tail-reader. The exact byte value of `TAIL_BYTES` was not read this session — not determined here; it does not affect correctness of the predicate for a live drill only seconds/minutes old.

**Direct consequence for the drill's Done criterion:** "pane A carries the resume line" = `user_issued_command_since(transcript_A, resume_command, t0)` returns `True`; "pane B carries none" = the same predicate over `transcript_B`, same command name and time window, returns `False`. The planner should call this exact function (or replicate its exact three-part rule) rather than grep raw on-screen pane text, because text merely typed/echoed into a terminal but never actually submitted to Claude Code would not produce a `type:"user"` row at all — only `term.sendText(..., false)` + a separate `\r` keystroke (see Q1) actually submits, and the transcript is the one artifact that proves submission happened, not merely display.

## Question 2 — Who produces the request (`C:\Users\User\.claude\hooks\auto-compact-sendkeys-daemon.ps1`)

[VERIFIED: auto-compact-sendkeys-daemon.ps1:298-377, read this session]

### `Resolve-Session($sid)` (`:298-317`)
Iterates every `*.json` file under `$sessionsDir` (default `~/.claude/sessions`, override `AC_SESSIONS_DIR`, `:292`). For each:
1. Parses the file as JSON; skips on parse failure (`:301`).
2. Skips unless `$s.sessionId -ceq $sid` (case-sensitive exact match, `:302` — note the code uses `-cne` i.e. "not case-sensitive-equal", so it `continue`s past non-matches).
3. Looks up the live process via `Get-CimInstance Win32_Process -Filter "ProcessId=$($s.pid)"`; skips if the process is not currently running (`:303-304`) — **this is the fail-closed "session is gone" case**.
4. Computes `$ft = $p.CreationDate.ToFileTimeUtc()` and compares to `$s.procStart` with tolerance `< 10` (FILETIME 100ns units) via `[Math]::Abs($rec - $ft) -ge 10` → skip if too different (`:305-308`) — same tolerance and rationale (CIM drops the last FILETIME digit) as `terminal_inbox.js`'s `sameProcStart`.
5. Walks up to 12 ancestor hops via `Win32_Process.ParentProcessId`, collecting each `ProcessId` into `$chain` (`:309-313`) — this IS the ancestor-chain resolution the question asked about: a straight `Get-CimInstance ... -Filter "ProcessId=$ParentProcessId"` loop, capped at 12 levels, stopping early if a parent lookup returns nothing (`-and $cur`).
6. Returns `@{ pid; procStart; ancestors }` on the first session file that matches all of the above; returns `$null` if no session file resolves (session id not found, OR found but its process is dead, OR procStart mismatch, OR — implicitly — after exhausting all files).

### `Request-Inbox($fl, $line, $key)` (`:319-336`)
- Calls `Resolve-Session $fl.sid`. **If it returns null** (no live claude.exe with matching procStart): logs `"inbox: session $sid not resolvable ...; foreground fallback"` and sets `$script:inbox[$key] = @{ sid; id=''; state='fallback'; at=Get-Date }` (`:321-324`) — **this is the "no answer possible" path, decided entirely locally, before any extension is even asked.** It does NOT write a ledger row itself at this point (see Poll-Inbox below for what happens to a `fallback` state — actually `Poll-Inbox` only ledgers `refused`; a `fallback` state falls through to the daemon's legacy SendKeys path elswhere, gated by `$legacyForeground`/`CPP_LEGACY_FOREGROUND_SENDKEYS=1`, see `:259` and `Send-Enter`/`Refuse-NoExact` at `:261-282`).
- If resolved: builds `$req` with exactly the fields `terminal_inbox.js::decide` expects: `id` (new GUID, no dashes — `[guid]::NewGuid().ToString('N')`), `session_id`, `text` (=`$line`, the command to submit), `claude_pid`, `proc_start`, `ancestors`, `created_ms` (Unix ms, UTC), `ttl_ms` (=`$inboxTtlMs`=60000 default) (`:326-328`).
- Writes atomically: temp file `<sid>.req.json.<PID>.tmp` written with `UTF8Encoding($false)` (**no BOM** — confirms extension.js's BOM-strip is defense-in-depth, not the normal path) then `Move-Item` to `<sid>.req.json` (`:331-333`).
- **Deletes any stale `<sid>.ack.json` first** (`:330`) — important: a leftover ack from a previous request-response cycle for the same session id would otherwise be misread by `Poll-Inbox` as an immediate answer to the NEW request. This delete-before-write is a correctness-critical step the drill's own harness (if it plants files directly) must replicate or avoid colliding with.
- Records local state `pending` keyed by `"<sid>|<flag mtime ticks>"` (`:335`, `$key` composite avoids collision across multiple flags for one sid).

### `Poll-Inbox($flags)` (`:338-377`) — where a refusal is recorded
- For every locally tracked inbox entry in `pending`/`deferred` state, reads `<sid>.ack.json` if present and checks `$ack.id -eq $e.id` (**id equality gate** — an ack for a different/stale request id is ignored, `:346`).
- `status == 'sent'` → local state → `sent`; logs `SENT via=extension ...`; deletes the matching flag file(s) (`:348-352`). **No `Write-LedgerRow` call for `sent`** — only the flag-file removal marks success; the ledger only records `refused` events from this function.
- `status == 'refused'` → local state → `refused`; logs `inbox: REFUSED by extension ...`; moves the flag file(s) to `auto-compact-refused*` name; **calls `Write-LedgerRow $e.sid 'refused' "terminal inbox refused: $($ack.reason)"`** (`:354-362`) — **this is the exact call that produces the phase's required "ledgered refused with its reason" evidence.**
- `status == 'deferred'` (and not already deferred locally) → local state → `deferred`, logged, no ledger row (still pending) (`:364-367`).
- **Timeout / no-answer path:** `$limit = if (deferred) { ttl_ms/1000 + 10 } else { $ackFirstSec }` (default `$ackFirstSec = 10`, override `AC_ACK_FIRST`, `:293-294,370`). If `age > limit`: state → `fallback`, deletes the `.req.json` (so no extension can claim it late), logs `"no extension answer in ${limit}s ...; foreground fallback"` (`:371-375`). **This path also does NOT call `Write-LedgerRow`** — a request nobody answers within 10s (or 70s if deferred) falls back to the legacy foreground SendKeys path (`Refuse-NoExact`/`Send-Enter`, gated by `$legacyForeground`) rather than being ledgered as `refused` by the inbox mechanism itself. **This matters for the drill design**: to get a ledgered `refused` entry, the drill needs the OWNING window's extension to actually answer with `status:"refused"` (i.e. trigger one of `terminal_inbox.js`'s refuse conditions while ownership still resolves to exactly one terminal) — NOT simply have no window own the request, which produces silent `fallback`, not a ledger row.

### Refusal / ledger locations summary
- `Write-LedgerRow` (`:236-241`) appends one JSON line per row to `<dir>/gsd-autorun-ledger.jsonl`, where `<dir>` = `$env:GSD_LONG_RUN_STATE_DIR` or `~/.claude/state` (`:238`). Row shape: `{ ts, session_id, event, detail }` (`:239`).
- Ledger writers observed in this file: `Refuse-Flag` (`:244-250`, a different code path — no-match-within-timeout on the OLD flag-file expectation mechanism, unrelated to inbox), `Refuse-NoExact` (`:261-266`, fires when NO exact-session delivery path exists at all AND legacy foreground is disabled — logs + moves flag + ledgers `'refused'` with detail `"no exact-session delivery: $why; foreground fallback disabled ..."`), and `Poll-Inbox`'s `refused` branch (`:361`, the one directly tied to `terminal_inbox.js::decide`'s refuse reasons). **The drill's Done criterion ("refused with its reason") is satisfied by either `Refuse-NoExact` or `Poll-Inbox`'s refused branch — the planner must pick which mechanism the drill deliberately triggers**, since they ledger different `detail` strings for a superficially similar outcome.

## Question 5 — The hazard to design around (`vault/terminal_slots.json` / `modules/zero-crash/hooks/terminal-slot-recorder.js`)

[VERIFIED: modules/zero-crash/hooks/terminal-slot-recorder.js:16-27,142-178, read this session]

The schema is explicit in the file's own header comment: `vault/terminal_slots.json` is `{ schema_version, slots: { "<cwd-as-key>": { session_id, started_at, transcript_path, previous_session_id } } }` (`:16-27`) — **one slot object per normalized cwd, full stop.** `normalizeCwd()` (`:142-148`) only lowercases the drive letter and normalizes slashes; it does nothing to disambiguate two sessions opened in the *same* directory.

The write path (`:169-178`) is unconditional and clobbering: on every `SessionStart` event, `data.slots[cwd] = { session_id: sessionId, ..., previous_session_id: prev ? prev.session_id : null }` — a plain object assignment. **If a second Claude Code session starts in a cwd that already has a slot entry, the second session's `SessionStart` hook completely overwrites the first session's entry**, demoting the first session's `session_id` to a `previous_session_id` field that nothing in this file's read path was found to consume (only the write side was in scope for this pass — not determined whether any consumer walks the `previous_session_id` chain). The file's own header comment says as much: cwd-as-proxy "fails gracefully (returns most-recent session for that cwd) when a project has multiple parallel sessions" (`:13-14`) — "fails gracefully" here means *silently returns the wrong session*, not that it detects and reports the ambiguity.

**The hazard, stated plainly, for the drill's design:**

1. **If pane A and pane B are opened in the SAME cwd**, `terminal_slots.json`'s single slot entry for that cwd will reflect whichever session's `SessionStart` fired *last* — i.e. pane B's session_id, once B starts. Any part of the drill's own setup or verification procedure that resolves "which session_id is pane A's" by reading `terminal_slots.json` (or anything built on it, e.g. `claude_smart_resume.ps1`'s tier-1/tier-2 lookups, or a human operator eyeballing the file) will silently get **B's session_id when it means A's**, or vice-versa depending on start order. This does NOT break the actual routing mechanism under test (`terminal_inbox.js::decide` never reads cwd or this file — it uses only the `ancestors` pid chain and `~/.claude/sessions/<pid>.json` identity, per Q1/Q2 above), but it CAN break the **operator's/harness's ability to correctly label which transcript file is "A's" and which is "B's"** when assembling the Done-criterion evidence — producing a result that looks like a pass or fail for the wrong pane, i.e. **unattributable**.
2. **Window title cannot substitute for this either.** CONTEXT.md states two sessions in one Cursor window are indistinguishable by title, and `V-ACPS-E-TITLE-MATCH-IS-NOT-IDENTITY` (Q4 above) is the codebase's own existing proof that a title match must never be read as identity.
3. **What actually IS a safe identity, per this codebase's own conventions** (cross-referencing Q1/Q2): the session's own `sessionId` + `pid` + `procStart` triple, read from `~/.claude/sessions/<pid>.json` (written at session start — not itself examined this session, "not determined" beyond what `Resolve-Session`/`decide()` read from it), and the transcript file located by `find_transcript(session_id)` (Q3) — i.e. **identify each pane by its own session_id, obtained from a source scoped to that specific process (the session file keyed by pid, or the transcript file keyed by session_id), never by cwd or window title.**

**What this implies for how the drill must create its second pane:** either (a) open pane B in a **different cwd** from pane A, so `terminal_slots.json` (if the drill's harness touches it at all) keeps two distinct, non-clobbering entries — the simpler and safer choice — or (b) if both panes must share one cwd (e.g. to exercise the SAME-window, SAME-`vscode.window.terminals`-array case that `terminal_inbox.js::ownedTerminals` is actually built to disambiguate, which is arguably the more interesting live case since it is the one where `decide()`'s "exactly one match" ownership logic actually gets exercised meaningfully), the drill must **never use `terminal_slots.json` or window title to identify which pane is A and which is B** — it must capture each session's own `session_id`/`pid` directly at the moment each pane's Claude Code process starts (e.g. from the `SessionStart` hook payload, or by reading each pane's own `~/.claude/sessions/<pid>.json` / matching transcript file by content), and carry that identity forward explicitly rather than re-deriving it later from a cwd- or title-keyed lookup.

**What would make the drill's result unattributable, stated plainly:** running both panes in the same cwd, then — when it comes time to write up "pane A got the resume line, pane B did not" — reaching for `terminal_slots.json`, `claude_smart_resume.ps1`, or the Cursor window title to figure out (after the fact) which session_id was which. Because the slot file only ever holds the LAST session to start in that cwd, and title cannot distinguish two sessions in one window at all, that after-the-fact lookup can silently return the wrong session for "A", making the recorded transcript evidence describe the wrong pane while still reading as a clean pass.
