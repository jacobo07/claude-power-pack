Measured gap 3 (02-CONTEXT `<evidence>`): the a7 lineage was RENEWED after its dead iterations. In the current
code a quarantined mission still hits its hours budget (plan_next decides "halt" before any provider hold is
consulted), GSD answers OK, `renewal_refusal` permits it, and the PREPARED successor takes the `launch` action --
which has no owner, so the relay-only `provider_hold` never runs. One fresh worker per renewal walks into the same
refusal. A renewal must not launder a quarantine.

Pillar B's wiring (CONTEXT decision "Preflight wiring into launch"): the launch path refuses with the typed reason
and a ledger row instead of launching; kill switch env var; fail-closed only on a measured NOT_READY.

Design (effect-authority rule: one effect, one authority, every entrance): a new `tools/mission_launch_gate.py`
is the single pre-launch authority; `gsd_mission.supervise` calls it in ONE hunk placed after the GSD check and
before turn-end / stop_owner / continue_worker / align / launch_worker, so a refusal changes nothing (no epoch, no
stop). The lineage logic lives in `provider_breaker.lineage_hold` (pillar C's owner); the env verdict comes from
`gex44_env_preflight` (plan 02-02). That keeps pillar C at its one gsd_mission hunk (plan 02-01) and gives pillar B
its one hunk here.

Activation (decided and justified): the env preflight runs only on a DECLARED mission plane --
`CPP_ENV_PREFLIGHT=on`, or `CPP_MISSION_PLANE` non-empty and `CPP_ENV_PREFLIGHT` not "off". The repeatable deploy
(plan 02-04) writes `export CPP_MISSION_PLANE=gex44` into the env's env.sh, so every env that deploy reaches is
gated and no undeclared host is: the laptop's live checkout is Windows and dirty by design and must never be judged
by GEX44 rules, and every existing hermetic suite (which would otherwise read the real HOME and the v18 node) stays
byte-for-byte unaffected without edits. The lineage hold is always on (subject to CPP_LAUNCH_GATE and the existing
CPP_PROVIDER_BREAKER switch).

Named debt (shrink-only, recorded in evidence by 02-04): `gsd_mission.py arm` launches its first worker through

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| supervisor -> worker launch | launching a worker spends quota and acts in the env; this is the side effect being gated |
| mission record -> lineage walk | renewed_from links are data from disk; cycles or missing records must not hang or crash the pass |
| preflight verdict -> launch decision | a wrong NOT_READY halts an env's missions; a wrong READY launches into a broken env |
