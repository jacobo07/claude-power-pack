## Decisions (taken by the planner, unattended; each reversible; none asks the Owner)

- **D6-01 Phase-local code only.** Every instrument Phase 6 writes lives under `.planning/workstreams/perf-construction/phases/06-ratchet-ukdl-and-hand-back/` (`PH`), stdlib only, run with `python3 -I`, registered nowhere, never imported from `tools/` or `modules/`. Nothing under `tools/`, `modules/`, `hooks/`, `vault/config/` is edited. Why: PERF-06 is inheritance, ratchet, UKDL and hand-back, not product behaviour; a new `tools/` file would reopen the reachability question (56 offenders must stay unchanged by name); and the phase-local instrument pattern is the one Phases 1, 2, 4 and 5 used. Only two tracked files outside the workstream are created: the Tower candidate note (D6-05) and the UKDL candidate file (D6-06).
- **D6-02 Inheritance is measured, not asserted.** (a) A manifest runs every standing gate of Phases 2-5 with its recorded expected marker and a closed verdict set (PASS, FAIL, TIMED_OUT, NOT_RUN, UNPARSED, BASELINE_MATCH, SKIPPED_BY_POLICY); a skipped row is never a pass and the footer prints judged versus total. (b) A mutant matrix plants one mutant per owner (Phase 2 bench_all, Phase 4 bench_all and resource_admission, Phase 3 construction_metrology, Phase 5 hook_critical_path_audit) in a scratch copy under /tmp and runs the standing gate `tools/test_bench_gate.py` and the owning suite on the mutant and on an unmutated control. Closed verdicts: ENFORCED (the standing gate fails on the mutant and not on the control), OWN_SUITE_ONLY (standing gate passes, owning suite fails), SURVIVED_ALL (neither fails: a test gap, reported), NOT_DISCRIMINATING (the control fails, or the failure does not trace to the mutant). Per F6 the planner expects Phase 3 and Phase 5 to come out OWN_SUITE_ONLY; the matrix measures it, and a surprise either way is recorded, not smoothed.
- **D6-03 No standing-gate wiring in this phase.** Wiring `test_construction_metrology.py` (10 s) or `test_hook_critical_path.py` (34 s) into `tools/test_bench_gate.py` would move the 30 s `bench-gate` row from 1.8 s to about 12 s or about 36 s and the second exceeds the budget. That is a budget decision on a shared standing gate, so it is an OWNER DECISION NEEDED, listed in the HANDOFF with its measured costs. Pick: leave unwired, list the two suites in the manifest and in the HANDOFF re-run command. Reversal: add a `V-BENCH-<NAME>-SUITE-WIRED` gate with a negative control as Phases 2 and 4 did.
- **D6-04 Ratchet: CONNECTED_SCRATCH, LIVE_BLOCKED.** The entries run through the real owner (`promote_with_evidence`, `verify_chain`, `checks.evaluate`) against a scratch root that is asserted not to be `vault/tower/baselines/`, and the refusal poles (missing negative control, same-run reuse, empty authority) are driven from the real code. No live generation and no family file is written. Reasons, in order: (1) F5, no family reaches this work, so a live entry would be unreachable; (2) F4, a live promotion needs an Owner authority and an unattended run has none (the scratch authority string says UNATTENDED and must not contain "Owner"); (3) F4 precedent, work with no family stays a candidates file until a second independent domain exists. Creating a family also adds triggers that change prompt injection for every matching prompt (`families.py` header), which is the Owner's call. OWNER DECISION NEEDED (12): create family `perf_construction` and a B0 now? Pick: no. Reversal: nothing to reverse; the Owner or the lead creates `vault/tower/families/perf_construction.json` and runs `promote` with an Owner authority using the command written in the candidate note.
- **D6-05 Tower candidate note.** `vault/tower/candidates/perf_construction.md`, in the shape of `ecommerce_storefront.md`: table of at most five entries, each with its verified origin quote, its evidence pointers and its status (PROMOTABLE_UNDER_OWNER_AUTHORITY or NOT_PROMOTABLE with the missing evidence part named per the owner's `evidence_problems`). An entry whose evidence fails the owner rule is listed as NOT_PROMOTABLE, never rounded up.
- **D6-06 UKDL candidates go to a new append-only file** `vault/knowledge_base/candidates/perf-construction-20261123.md` (F7). No edit of `vault/knowledge_base/ukdl-universal.md`, `session_lessons.md`, `vault/hard_rules/*`, `governance/*`, `wiki/*`. Each candidate has an id, kind (HR, PR or T), one statement, evidence pointers that resolve to existing files, the plane that observed it, scope (`#CROSS-PROJECT` or `#PP-LOCAL`), an ownership-sweep result (an existing owner named, or NEW with the grep), and status `CANDIDATE - NOT PROMOTED`. At most one HR candidate and only if it has a trigger, a stop and an evidenced cost; the default kind is PR or T. A candidate whose sweep finds an existing owner is recorded as EXTEND_EXISTING_OWNER and not drafted as new (the discipline of HR-NOVELTY-001, applied in small).
- **D6-07 HANDOFF facts are generated.** Counts (unknowns per phase, LP items, OWNER DECISION NEEDED lines, files touched) are produced by `handoff_check.py inventory` from the phase files and `git diff --name-only a0e12830 HEAD`, never typed. The owner summary opens with the literal line `Creation speed on the laptop: UNKNOWN`. - **D6-08 Bookkeeping.** STATE.md gets an appended "Phase 6" decisions block (OWNER DECISION NEEDED (11) to (13) and the carried debt). Its position fields, `ROADMAP.md`, `REQUIREMENTS.md` and the ROOT milestone are not edited; the orchestrator advances them (the GSD progress commands cannot parse this STATE.md).
- **D6-09 Skipped suite stays UNJUDGED.** `tools/test_s9_redteam.py` (814 s) is SKIPPED_BY_POLICY in the manifest with its last recorded count and its Phase 4 caveat; `--include-slow` exists and is not run unattended.
